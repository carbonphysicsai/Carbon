# Protocol Change Routing

These stable routes explain placement. The active wave board and selected ticket control implementation authorization.

## Add a new Challenge

Route a new physical job from authored semantics through real integration and human qualification.

**Stable route ID:** `new-challenge`

**Start:** Define the intended physical decision and claim before choosing the generator, solver, score, or model.

**Waves:** Wave B, Wave C, Wave D, Wave H, Wave I

**Current ticket anchors:** B-02A, B-03, B-04, B-05, B-06, B-E1, B-E2, B-E3, B-GATE

**Why this route:** A Challenge is a connected scientific object. Population, case generation, reference truth, measurements, uncertainty, evidence use, and qualification must agree on the same identity.

### Decisions to name

- PhysicalSystemSpec and intended claim
- Candidate input and output contract
- P, Q, w and population roles
- SamplingPlan, strata, censoring, replacement, and sufficiency
- Generator applicability and conformance
- Primary and witness reference adequacy and uncertainty
- Measurements, gates, transforms, floors, and weights
- Reconstruction variance and decision-resolution policy
- Disclosure, rights, and Launch Bar inputs
- Prospective frontier-promotion evidence and policy
- Separate settlement obligation and treasury policy where applicable

### Human-owned or human-approved inputs

- Real physical identity and claim
- Production population and SamplingPlan
- Reference adequacy
- Scientific thresholds and evidence weights
- Exact LIVE activation
- Frontier promotion and settlement activation

### Repository flow

1. Create or update the owning wave ticket
2. Record working and reserved decisions in .agent/DECISIONS.md
3. Route SciML and technical decisions through issue #42
4. Route owner-reserved decisions through issue #41 when deferred
5. Implement through bounded PRs and exact tests
6. Record evidence and maturity ceilings
7. Route any later frontier promotion through Wave H and settlement through Wave I
8. Update hub status and links after the repo changes

### Repository authority

- [Scientific Challenge Authoring Contract](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Scientific_Challenge_Authoring_Contract.md)
- [Wave B controlling board](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/.agent/WAVE_B.md)

> This route explains placement. The active wave board must authorize the exact implementation sequence.

## Add or change a model architecture

Place architecture work according to whether it changes a bounded catalog component, a reconstruction adapter, or the permitted search space.

**Stable route ID:** `model-architecture`

**Start:** Name the exact change: catalog component, family adapter, construction method, or deployable system. Those changes belong to different waves.

**Waves:** Wave B, Wave C, Wave F, Wave J, Wave K, Wave L, Wave M

**Current ticket anchors:** B-07R, B-02B, B-02C, B-05, B-06, B-07F, B-E1, B-GATE

**Why this route:** An architecture label cannot carry scientific authority. Carbon needs exact assembly, reconstruction, measurement, and qualification bindings for the resulting artifact.

### Decisions to name

- CandidateAssemblyContract placement
- ParameterCatalog and StrategyCompiler representation
- Allowed structural component and R_strategy roles
- Reconstruction environment and resource limits
- Reference and measurement applicability
- Cross-family comparison contract
- Artifact and runtime identity
- Product Battery and requalification triggers

### Human-owned or human-approved inputs

- Real catalog values and permitted training policies
- Security acceptance for execution freedom
- Scientific applicability and measurements
- Product qualification scope

### Repository flow

1. Classify the architecture change
2. Attach it to the current owning ticket or create a later-wave ticket
3. Record compatibility and migration cost
4. Add reconstruction and invariant tests
5. Run scientific comparison only under registered contracts
6. Create qualification records for deployable artifacts

### Repository authority

- [Candidate Assembly and Strategy Compiler Contract](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Candidate_Assembly_and_Strategy_Compiler_Contract.md)

> Wave B may expose bounded, Challenge-owned structural components. Broad model-family neutrality belongs to Wave J, and arbitrary construction programs remain later-wave work.

## Add or change a miner prior

Route prior work through immutable schema, publication controls, deterministic provision, and leakage testing.

**Stable route ID:** `miner-prior`

**Start:** State the estimand, source cohort, lag, granularity, eligibility, and intended miner decision before creating content.

**Waves:** Wave B, Wave E

**Current ticket anchors:** B-07R, B-07S, B-07A, B-07B, B-07D1, B-07D2, B-07D3, B-07E, B-07G, B-E4, B-GATE

**Why this route:** A prior can help search, but it can also leak the hidden exam, encode rights violations, personalize unfairly, or predict official outcomes.

### Decisions to name

- Public estimand and cohort
- Source eligibility and evidence class
- Lag, cadence, granularity, and diversity floor
- Immutable PriorPack identity
- Publication eligibility and cumulative disclosure
- Rights and reuse policy
- Exact-byte provider behavior
- Utility and leakage gauntlet

### Human-owned or human-approved inputs

- First real prior content
- Release approvers and rights
- External activation
- Signer or key custody
- Utility effect floor and leakage limit

### Repository flow

1. Define PriorPack in B-07D1
2. Stage only TEST_ONLY publication in B-07D2
3. Serve exact approved bytes through B-07D3
4. Retain lineage through B-07B
5. Test utility, leakage, poisoning, and cheating in B-E4
6. Keep official score, rank, gate, and winner prediction unavailable

### Repository authority

- [Wave B Miner MCP Research Contract](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Miner_MCP_Wave_B_Research_Contract.md)
- [Research Resource Policy Contract](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Research_Resource_Policy_Contract.md)

> Wave B priors remain immutable Challenge-level artifacts. Server-side personalization and qualified learned public publication are not active capabilities.

## Change a reference or truth path

Route truth assets, primary and witness roles, uncertainty, access, typed failure, operations, and fail-closed behavior through their owning records.

**Stable route ID:** `reference-truth`

**Start:** Name the reference role, truth asset, access mode, applicability envelope, uncertainty, and failure behavior before changing a solver or adapter.

**Waves:** Wave B, Wave C, Wave D

**Current ticket anchors:** B-04, B-E1, B-E2, B-E3

**Why this route:** Reference output is not automatically truth. Carbon must bind policy, exact assets, access, independence, applicability, uncertainty, and typed failures without collapsing reference failure into candidate failure.

### Decisions to name

- ReferencePolicy and exact truth-asset identity
- Primary and witness roles and independence
- Applicability envelope and discrepancy policy
- Uncertainty representation and propagation
- ReferenceAccessMode, rights, privacy, and operations
- Typed failure, disagreement, retry, and fail-closed behavior

### Human-owned or human-approved inputs

- Reference adequacy
- Production truth assets and access rights
- Scientific uncertainty acceptance
- Prospective change timing for a LIVE Challenge

### Repository flow

1. Open a superseding decision instead of rewriting history
2. Update reference policy, asset, access, and provenance identities
3. Classify operations, migration, and evidence invalidation
4. Add primary/witness disagreement and typed-failure fixtures
5. Keep reference failure separate from candidate failure
6. Re-run qualification evidence before activation

### Repository authority

- [Julia truth-oracle runtime](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Runtime_Julia_Truth_Oracle.md)
- [Evidence and Envelope Standards](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Evidence_and_Envelope_Standards.md)

> A successful solver run is not reference qualification. Missing or failed truth remains typed and fail closed.

## Change measurement or scoring

Keep measurement definition, uncertainty, Score Pack evidence use, admissibility, ranking, frontier policy, and settlement in separate owning records.

**Stable route ID:** `measurement-scoring`

**Start:** Classify whether the change affects a measurement operator, uncertainty policy, Evidence Use Contract, admissibility, ranking, promotion, or settlement before editing the engine.

**Waves:** Wave B, Wave C, Wave D, Wave H, Wave I

**Current ticket anchors:** B-05, B-06, B-E1, B-E2, B-E3, B-GATE

**Why this route:** Measurement authority, evidence applicability, Score Pack use, ranking, frontier promotion, and economic settlement answer different questions. A result or business request cannot silently change the scientific ruler.

### Decisions to name

- Measurement contract, operator, discretization, and applicability
- Uncertainty floor, transform, censoring, and aggregation
- Score Pack binding and admissibility before ranking
- Challenge-bound score and historical comparability
- Evidence use, requalification, and prospective migration
- LeaderReplacementPolicy and separate FrontierAdvanceEvent
- Settlement obligation and treasury policy separation

### Human-owned or human-approved inputs

- Measurement qualification and scientific thresholds
- Evidence weights and real admissibility policy
- Frontier-promotion acceptance
- Live economics, treasury, and settlement activation

### Repository flow

1. Open a prospective superseding decision instead of rewriting history
2. Update exact measurement and Score Pack identities
3. Classify evidence invalidation and migration
4. Test admissibility separately from ranking
5. Keep leaderboard nomination separate from frontier promotion
6. Keep science separate from settlement
7. Re-run qualification before activation

### Repository authority

- [Scoring specification](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Scoring.md)
- [Evaluation Evidence and Validator Audit](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/Design_Specs/Evaluation_Evidence_and_Validator_Audit.md)

> Customer payment, sponsor size, economic policy, prior similarity, and mock or practice metrics cannot enter official score unless a future registered scientific contract gives a metric a legitimate scientific role.

## Repair a protocol defect or invariant regression

Attach the defect to the ticket that owns the violated contract, then preserve the repair and evidence trail.

**Stable route ID:** `protocol-defect`

**Start:** Describe the observed behavior and the violated invariant or contract. Do not classify a scientific failure as an infrastructure bug without evidence.

**Waves:** Wave A, Wave B, Wave C, Wave D, Wave E, Wave F, Wave G, Wave H, Wave I, Wave J, Wave K, Wave L, Wave M, Wave N

**Current ticket anchors:** No current Wave B ticket anchor is captured.

**Why this route:** A bug needs one owning node even when its effects cross the system. The map should show placement and impact while the PR carries the technical detail.

### Decisions to name

- Owning wave and ticket
- Failure class: strategy, reference, generator, measurement, infrastructure, security, or disclosure
- Affected identities and evidence
- Repair versus superseding protocol change
- Regression and invariant tests
- A12 coverage when an always-on invariant regresses
- Whether status or downstream dependency changes

### Human-owned or human-approved inputs

- Scientific re-interpretation
- Security acceptance after a material exposure
- Production incident acceptance

### Repository flow

1. Attach the issue to the ticket or contract that owns the violated behavior
2. Set exactly one primary map_ref and list every affected node
3. Repair in a PR
4. Add a failing regression test and invariant where applicable
5. Record review, merge, and evidence
6. Update the hub when team understanding, placement, status, dependency, boundary, maturity, or primary links change

### Repository authority

- [Always-on invariants](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/.agent/INVARIANTS.md)
- [Agent decisions log](https://github.com/carbonphysicsai/Carbon/blob/bd479bf478fee193d9d81dec34a5b73bf623a098/.agent/DECISIONS.md)

> Post-merge history stays intact. Record the correction or superseding decision rather than editing evidence to hide the original defect.

**Waves:** Wave F, Wave G, Wave M

**Current ticket anchors:** No current Wave B ticket anchor is captured.

**Why this route:** A commercial wrapper can change data access, deployment identity, support, acceptance, and rights without changing the scientific standard.

### Decisions to name

- Evidence reuse class
- Deployment identity
- Deliverable and acceptance contract

### Human-owned or human-approved inputs

- Security qualification
- Commercial approval
- Customer-specific scientific scope

### Repository flow

1. Create CommercialEngagementSpec
2. Qualify the requested topology
