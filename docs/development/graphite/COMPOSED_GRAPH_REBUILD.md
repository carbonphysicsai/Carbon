# Composed graph reconstruction (PLT-25 / S2)

The prospective `carbon.battery.composed-graph.v1` record combines verified
Level 4 graph documents with the existing composed Carbon trainer. GraphModel
owns network preparation, initialization, forward execution and self-contained
state; the trainer applies the selected pool, SpecMuon, L3 routine/line search,
and a sole objective. Existing single-level records and routes remain intact.

A forward-only graph can use an L1 expression. A verified loss-role graph plus
an L1 expression refuses before training and envelope/freeze acceptance, naming
`loss_expressions+composition_graphs`. Permission `loss_override: graph` alone
does not imply a loss document. Admitting two objectives requires a prospective
named Validator precedence ruling; this implementation keeps that pair refused.

Reconstruction stages the verified workspace and Carbon graph modules, patches
both model creation and graph-state serialization, and uses the existing graph
state loader for inference. Envelope checks depend on graph-field presence.
The base recipe strips all registered widened fields using checked public
metadata; the validator import closure cannot reach development_variants.

## Bound cost evidence

`composed_graph_cost.compile_in_isolation` is the supplemental producer API for
an already compiled construction, workspace and paired G5 result. It stages a
fixed Carbon program in the existing development/testnet compile lane, with the
same deadline/provenance/resources. The program captures the actual composed
main loop and separately compiles its full-batch loss/gradient for L3; it stops
before training or polish. Capture and subsequent full-batch compilation share
the recipe-specific precision context, restored on every exit. It emits no trained state.

The profile binds the canonical recipe and full record, verified documents and
allowlist, complete G5 evidence, fixed algorithm source bytes, image, scope,
objective, effective batch, precision and actual graph parameter count. The
cost consumer validates metadata and never prepares or compiles graph code on
the evaluator host. It counts the complete main step once, applies the existing
registered line-search cap to full-batch gradient work, and adds the existing
dense `4*p^2` term independently. A supplied `k_polish` retains its established
override precedence while preserving that dense term. Calibration remains
HUMAN_INPUT where unsupplied.

Missing/stale/mixed profiles and opaque operations refuse explicitly. Recursive
inspection detects actual SVD and other opaque numerical work, including nested
data-dependent while. Matrix SpecMuon currently produces a named unpriced
`muon_spectral` refusal; no speculative SVD coefficient is introduced. A flag
without an actual opaque operation does not itself cause refusal.
