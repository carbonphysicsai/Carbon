# G-FEAS threshold retuning preparation

**DEVELOPMENT diagnostic only.** This command does not change the v3 rule or
select a new threshold. It uses the owner's `exceeds` comparison: a recipe
fails G-FEAS only when its scoring-set false-feasible rate is strictly above
the supplied threshold. Registry v5 records the prospective exact-0.05 fix;
older registry v4 results keep their historical at-or-above interpretation.

Run the public synthetic demonstration:

```sh
python -m scripts.dev.battery.g_feas_retune \
  --public-synthetic-demo --bootstrap-replicates 300 --seed 17 \
  --output new-synthetic-curves.json
```

The checked-in [aggregate output](synthetic-curves.json) is generated by this
command. It combines #961's **public synthetic** v3 robustness controls with
two additional **ASSUMPTION** good boundary recipes at G-FEAS rates 0.02 and
0.08. These are toy numbers, not measured recipe evidence. At thresholds
0.005, 0.02, 0.05 and 0.1, respectively, the toy accepted-member mean
false-feasible rates are 0, 0.0025, 0.00751 and 0.01476; the predeclared
good-recipe fail rates are 1/3, 1/6, 1/6 and 0; and τ-b is about −0.024,
0.186, −0.186 and 0. These values show that the command exposes trade-offs.
They say nothing about the threshold to adopt for actual miners.

## Run when stage A summaries arrive

```sh
python -m scripts.dev.battery.g_feas_retune \
  --input DEVELOPMENT-summary.json --bootstrap-replicates 2000 --seed 17 \
  --output new-development-curves.json
```

The input has schema `carbon.battery.g-feas-retune-input.v1`, scope
`PUBLIC_DEVELOPMENT` or `DEVELOPMENT_SUMMARY_ONLY`, source/screening/Q3/decision
SHA-256 digests, the registry v5 SHA-256 digest, a good-recipe selection
receipt digest, a sorted explicit `thresholds` grid, and `members`. Each
member summary has a member and recipe identity, v3-report and development
value-receipt digests, state, `a`, `q3_regret`, `g_feas`, and `decision_loss`.
All four numbers must be from the **same recipe** under compatible registered
v3 screening, settled Q3 and common resolved DEVELOPMENT decision evidence.
`g_feas` is the scoring-set measure, never the Q3 outcome. Good recipe IDs
must be declared before inspecting the threshold curves; with multiple seeds,
any failed seed fails that recipe in the diagnostic rate.

The command reports no member names, recipe names, case IDs, references or
individual scores. A non-SCORED row produces `INSUFFICIENT_EVIDENCE` and an
aggregate state count; no incomplete member is silently removed. Bootstrap
intervals resample recipe clusters. The false-feasible metric is the **mean
of member rates among passing members**, not a pooled case rate or an exam
failure probability. The primary τ uses the scorer's gate-fail floor so every
failed member ranks below every passing member; a passing-only τ is also
reported. Undefined τ stays null.

The committed run-5 Q1 panel and EV4/EV5 studies do **not** contain matched
per-member v3 accuracy, settled Q3 regret and scoring-set G-FEAS values. Their
historical practice/exam scores and public decision values cannot be
substituted. Thus no numerical real-recipe threshold curve is available from
main today. Stage A's digest-bound development summary records can be passed
after collection, with no hidden cases, prediction bundles or reference values
leaving their custodian. Test Lead interprets the curves; the owner alone
chooses any prospective threshold and rule version.
