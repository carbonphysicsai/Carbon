# Protocol Change Routing

The routes below explain placement. The active wave board controls implementation authorization.

## Add a new Challenge

Route a new physical job from authored semantics through real integration and human qualification.

**Start:** Define the intended physical decision and claim before choosing the generator, solver, score, or model.

**Waves:** B, C, D, H

**Current ticket anchors:** B-02A, B-03, B-04, B-05, B-06, B-E1, B-E2, B-E3, B-GATE

**Why this route:** A Challenge is a connected scientific object. Population, case generation, reference truth, measurements, uncertainty, evidence use, and qualification must agree on the same identity.

### Decisions to name

- PhysicalSystemSpec and intended claim
- Candidate input and output contract
- P, Q, w and population roles
- SamplingPlan, strata, censoring, replacement, and sufficiency
- Generator applicability and conformance
- Primary and witness reference adequacy and uncertainty
- Measurements, gates, transforms, floors, and weights
- Reconstruction variance and decision-resolution policy
- Disclosure, rights, and Launch Bar inputs

### Repository flow

1. Create or update the owning wave ticket
2. Record working and reserved decisions in .agent/DECISIONS.md
3. Route SciML and technical decisions through issue #42
4. Route owner-reserved decisions through issue #41 when deferred
5. Implement through bounded PRs and exact tests
6. Record evidence and maturity ceilings
7. Update hub status and links after the repo changes

> This route explains placement. The active wave board must authorize the exact implementation sequence.

## Add or change a model architecture

Place architecture work according to whether it changes a bounded catalog component, a reconstruction adapter, or the permitted search space.

**Start:** Name the exact change: catalog component, family adapter, construction method, or deployable system. Those changes belong to different waves.

**Waves:** B, C, F, J, K, L, M

**Current ticket anchors:** B-02B, B-05, B-07F, B-E1, B-GATE

**Why this route:** An architecture label cannot carry scientific authority. Carbon needs exact assembly, reconstruction, measurement, and qualification bindings for the resulting artifact.

### Decisions to name

- CandidateAssemblyContract placement
- ParameterCatalog and StrategyCompiler representation
- Allowed structural component and R_strategy roles
- Reconstruction environment and resource limits
- Reference and measurement applicability
- Cross-family comparison contract
- Artifact and runtime identity
- Product Battery and requalification triggers

### Repository flow

1. Classify the architecture change
2. Attach it to the current owning ticket or create a later-wave ticket
3. Record compatibility and migration cost
4. Add reconstruction and invariant tests
5. Run scientific comparison only under registered contracts
6. Create qualification records for deployable artifacts

> Wave B may expose bounded, Challenge-owned structural components. Broad model-family neutrality belongs to Wave J, and arbitrary construction programs remain later-wave work.

## Add or change a miner prior

Route prior work through immutable schema, publication controls, deterministic provision, and leakage testing.

**Start:** State the estimand, source cohort, lag, granularity, eligibility, and intended miner decision before creating content.

**Waves:** B, E

**Current ticket anchors:** B-07A, B-07B, B-07D1, B-07D2, B-07D3, B-E4, B-GATE

**Why this route:** A prior can help search, but it can also leak the hidden exam, encode rights violations, personalize unfairly, or predict official outcomes.

### Decisions to name

- Public estimand and cohort
- Source eligibility and evidence class
- Lag, cadence, granularity, and diversity floor
- Immutable PriorPack identity
- Publication eligibility and cumulative disclosure
- Rights and reuse policy
- Exact-byte provider behavior
- Utility and leakage gauntlet

### Repository flow

1. Define PriorPack in B-07D1
2. Stage only TEST_ONLY publication in B-07D2
3. Serve exact approved bytes through B-07D3
4. Retain lineage through B-07B
5. Test utility, leakage, poisoning, and cheating in B-E4
6. Keep official score, rank, gate, and winner prediction unavailable

> Wave B priors remain immutable Challenge-level artifacts. Server-side personalization and qualified learned public publication are not active capabilities.

## Change reference truth, measurement, or scoring

Keep truth access, measurement definition, evidence use, and engine execution in separate owning records.

**Start:** Classify whether the change affects the truth source, the measured property, the evidence policy, or the runtime engine.

**Waves:** B, C, D, H

**Current ticket anchors:** B-04, B-05, B-E1, B-E2, B-06, B-E3

**Why this route:** Changing one layer can change the scientific claim. Carbon must preserve exact identities and review whether existing evidence remains comparable.

### Decisions to name

- Reference role and applicability
- Independence and witness policy
- Measurement operator and discretization
- Floor and uncertainty treatment
- Admissibility and ranking use
- Requalification and frontier comparability

### Repository flow

1. Open a superseding decision instead of rewriting history
2. Update exact contract identities
3. Classify migration and evidence invalidation
4. Add failure and disagreement fixtures
5. Re-run qualification evidence before activation

> A customer request, runtime convenience, or observed result cannot change a registered scientific ruler retrospectively.

## Change a protocol contract

Route a cross-cutting protocol change through authority classification, bounded supersession, migration, and evidence.

**Start:** Identify which authority plane owns the meaning before editing code or a public interface.

**Waves:** A, B, C, H, I, L

**Current ticket anchors:** B-07R, B-07S, B-07A, B-07G, B-GATE

**Why this route:** Protocol changes often affect identity, canonical bytes, lifecycle, errors, compatibility, security, and downstream evidence at once.

### Decisions to name

- Owning authority and affected invariants
- Backward compatibility and versioning
- Canonicalization and exact identity
- Lifecycle and terminal outcomes
- Error precedence and fail-closed behavior
- Migration and historical preservation
- Security and disclosure effects

### Repository flow

1. Place one primary map_ref
2. Create a bounded superseding decision
3. List downstream tickets and migration cost
4. Update owning contract before implementation
5. Implement and test exact compatibility behavior
6. Preserve old evidence and mark supersession
7. Update hub routing after merge

> Later-wave architecture does not authorize implementation inside the active wave unless the current ticket names the compatibility seam.

## Fix a bug or defect

Attach the defect to the ticket that owns the violated contract, then preserve the repair and evidence trail.

**Start:** Describe the observed behavior and the violated invariant or contract. Do not classify a scientific failure as an infrastructure bug without evidence.

**Waves:** A, B, C, D, E, F, G, H, I, J, K, L, M, N

**Current ticket anchors:** B-GATE

**Why this route:** A bug needs one owning node even when its effects cross the system. The map should show placement and impact while the PR carries the technical detail.

### Decisions to name

- Owning wave and ticket
- Failure class: strategy, reference, generator, measurement, infrastructure, security, or disclosure
- Affected identities and evidence
- Repair versus superseding protocol change
- Regression and invariant tests
- Whether status or downstream dependency changes

### Repository flow

1. Create the issue or bounded ticket record
2. Set map_ref and affected nodes
3. Repair in a PR
4. Add a failing regression test and invariant where applicable
5. Record review, merge, and evidence
6. Update the hub only when placement, status, dependency, or links change

> Post-merge history stays intact. Record the correction or superseding decision rather than editing evidence to hide the original defect.

## Add a commercial or private deployment mode

Route customer-facing capability through rights, privacy, truth access, delivery, acceptance, qualification, and lifecycle.

**Start:** Define the customer decision, privacy profile, truth-access mode, promised deliverable, and rights before promising topology or evidence.

**Waves:** F, G, M

**Current ticket anchors:** No current Wave B ticket anchor

**Why this route:** A commercial wrapper can change data access, deployment identity, support, acceptance, and rights without changing the scientific standard.

### Decisions to name

- Privacy profile
- ReferenceAccessMode
- Customer data and solver rights
- Evidence reuse class
- Deployment identity
- Deliverable and acceptance contract
- Support and requalification triggers

### Repository flow

1. Create CommercialEngagementSpec
2. Qualify the requested topology
3. Attach the exact scientific program and evidence identity
4. Separate sponsor rewards from Carbon revenue
5. Define acceptance and lifecycle
6. Record professional advice and unresolved rights

> The business canon permits these product directions, but Carbon cannot sell a mode as implemented until technical and contractual qualification exists.
