## What the request means

The owner requests approximately 200–5,000 CPU-hours per job and 48–200 vCPU. These are OWNER-REQUEST bounds, not measurements. CPU-hours need a machine and thread definition: Hetzner CCX and GCP C3D count hardware threads, whereas AWS C7a and Azure Fasv6 expose a full physical core per vCPU. AX162 has 48 physical cores and SMT, hence 96 advertised threads. Comparing tariff divided by advertised vCPU is a purchasing comparison, not solver price-performance. [Hetzner CCX FAQ](https://docs.hetzner.com/cloud/servers/faq/), [AWS C7a](https://aws.amazon.com/ec2/instance-types/c7a/), [GCP C3D specifications](https://docs.cloud.google.com/compute/docs/general-purpose-machines#c3d_series), [Azure Fasv6](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/compute-optimized/fasv6-series), [AX matrix](https://www.hetzner.com/dedicated-rootserver/matrix-ax/).

At perfect scaling, 5,000 comparable worker CPU-hours divided by 200 comparable workers takes 25 hours; divided by 48 takes 104.17 hours. These are DERIVED lower bounds, not forecasts. Independent cases can fill many machines; a single tightly coupled solve may not. The cost model includes utilization, interruption and provisioning uncertainty, and a separate physical-core interpretation.

## Confidential VM options

These are separate procurement candidates, not a declaration that Carbon's worker or sealing workflow is qualified. They retain the cloud account, regional/family quota, stock and guest administrator constraints above. First public-only implementation planning adds **ASSUMPTION 1 / 3 / 10 elapsed days** for image, attestation and key-release work, on top of provisioning; a mature pre-approved workflow could avoid that one-time delay.

Date-sensitive operational evidence: Google's September 23 release note makes C4 standard TDX generally available, while one configuration table still calls it Preview. The selected C3 route avoids relying on that documentation seam. July guidance reports SNP boot/performance changes from August through an expected November resolution; recent firmware bulletins also require patch-status review. These are vendor-reported conditions, not measured Carbon overheads. The selected SNP/TDX maximum supported size remains HUMAN_INPUT where the configuration page does not publish a clear limit; a whole-family maximum must not be represented as an attested-size entitlement. [Current release notes](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/release-notes).

An honest claim is: **a correctly configured, patched and attested SNP/TDX VM is designed to prevent the cloud host/hypervisor operator from directly reading guest memory and CPU state**. It is not an unconditional statement that nobody at the provider can ever obtain material. Guest administrators and workloads can read plaintext, compromised guest code can export it, and disk, network, logs, crash dumps, management identities, availability and hardware/firmware trust remain relevant. The source guarantees are platform threat-model claims, not Carbon-tested guarantees. [Azure FAQ](https://learn.microsoft.com/en-us/azure/confidential-computing/confidential-vm-faq), [GCP overview](https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/confidential-vm-overview), [NVIDIA attestation responsibility mapping](https://docs.nvidia.com/enterprise-reference-architectures/deploying-proprietary-models-confidential-compute-self-hosted-vms/latest/appendix-c.html).

Proposed future custody acceptance record: approved immutable image and solver digests; independent freshness-bound attestation before releasing material keys; least-privilege owner key custody; encrypted boot/data/swap; restricted ingress/egress and administrative access; sanitized logs; encrypted authenticated checkpoints; result integrity and reference reproducibility; deletion of every snapshot/backup and destruction/revocation of job keys. This is a recommendation for the security owner, not a deployed mechanism. Hidden-evaluation allow-list and seed non-disclosure remain unchanged.

Ordinary full VMs solve the **guest administration** problem without changing a non-root worker contract: infrastructure can provide host SSH/sudo and run the pinned solver worker as its non-root user. Installing sshd inside an already-running restricted pod is neither necessary nor evidence of a CPU-capacity shortage. Future image/launcher changes belong to the infrastructure owner. No such changes were made here.

## Recommendation and decision points

**This week:** owner asks Robot sales/support for an **in-stock AX162-1 with the regular tariff and a firm order/first-run estimate**, using the already established account described by the owner. Research has not verified that relationship or stock. For an advertised-thread budget up to 192, two such hosts are a plausible fleet; for 5,000 physical-core-hours within roughly a day, use a quota-ready C7a 192-core host or a larger confirmed bare-metal fleet. If Robot cannot confirm delivery, next ask Scaleway to confirm identity-validated Iridium stock; it has published hourly pricing and a clear server-cleaning policy. AWS/Azure Spot are economical **after** quota confirmation, not guaranteed new-account escape routes.

**Standing second server:** AX162-1, with monthly planning low/base/high €317.30 / €612.30 / €842.30 (limited / regular -1 / regular -2 tariff scenarios) and setup €39 / €304 / €419. Prefer the regular -1 base; LTD is optional, and the high scenario is a different configuration, not a statistical price confidence bound. Dollar tariff scenarios $372.10 / $722.10 / $992.10; setup $39 / $359 / $494. IPv4, tax and options extra. If independent-provider availability matters more than lowest monthly cost, Scaleway I520 is €569.99/month plus €569.99 initial monthly commitment fee; hourly is €1.562 and has no commitment fee. The choice remains commercial authority.

Before a sealed run, the infrastructure/security owner must resolve actual quote, capacity, CPU-hour definition, RAM per concurrent case, public-only worker/image readiness, account permissions, restart semantics, deletion record and accepted host threat model. No public source proves any candidate usable on Carbon's account **today**. Confidential VMs are the strongest investigated hardware direction for reducing host-memory trust, but they should not hold this week's deadline until a public-only acceptance workflow exists.
