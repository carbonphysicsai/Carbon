# PLATING-BAND-NARROWING-V3-01: public D3 comparison

**Decision status:** insufficient evidence to register a v3 band or choose a reference method. `battery-plating-ref-v2` remains the only registered label rule here. This is a development analysis, not a relabel, qualification or spend request. The owner reserves the method, run figure and v3 band; the Carbon Validator owns reference-rule review.

## What the committed evidence establishes

The reproducible aggregate [PUBLIC_D3_OPTIONS.json](PUBLIC_D3_OPTIONS.json) is generated by `python -m scripts.dev.battery.plating_band_v3_options --sensitivity-band-mv 0.1 --sensitivity-band-mv 0.2 --sensitivity-band-mv 0.4`. The CLI accepts only three committed public D3 files by exact SHA256, requires `rule` in `V2_RULES`, recomputes every v2 label and joins the older draft by case ID. It counts by the `source` field; all 772 IDs happen to start `ev4:` even though 695 rows have source `pdd`.

There are 669 mesh160-solved rows, of which v2 labels 114 FEASIBLE, 447 INFEASIBLE and 108 UNRESOLVED. Another 103 are pending mesh160 and UNRESOLVED. Relative to the D3 **draft** 0.6 mV label, 46 mesh160-solved FEASIBLE rows became v2 UNRESOLVED. This is not a historical rescore. Only 6 of those 46 have the mesh40/80/160 convergence ladder; the other 40 lack mesh80. No public successful mesh320 rung exists.

In the 67-rung sample, observed convergence orders range **0.468–1.382**. Holding each observed mesh80-to-160 delta fixed while varying order across that range produces a maximum extrapolated-reference interval width of **0.782 mV** in the sample. That interval is a sensitivity calculation, not a calibrated error bound or an allowable v3 band. For the six lost-FEASIBLE cases with all rungs, illustrative extrapolated bands of 0.1, 0.2 and 0.4 mV would recover all six using each case's fitted order; using the sample's worst observed order recovers **4, 3 and 2** respectively. None of these figures estimates recovery among the other 40, validates a new band, or proves the Richardson method. The two routes cannot be ranked by recovered cases or approved cost yet.

## Conditions to check before a prospective v3 decision

1. **Coverage and chronology:** collect mesh80 for every in-band case proposed for the new method, including pending mesh160 cases once solved; retain an independent convergence subset and digest-bound records. Keep v2 and its historical results unchanged.
2. **Extrapolation error:** pre-register how order uncertainty, residual discretization error, mesh/solver tolerances and unsampled cases determine a new extrapolated-reference band. Test the bound on the full target set; a narrower point estimate alone does not justify a narrower band. Recheck the pre-registered v2 stop triggers (residual >0.374 mV, order <0.47, extrapolation <0 with mesh160 ≥1.0 mV, or new upper-window bias >3.5 mV) on all applicable new records. Failure requires re-derivation, never retention by default.
3. **Recovery calculation:** evaluate the new registered label rule on **all 46** lost-FEASIBLE cases with resolved references and count still-UNRESOLVED cases separately. Do not use the six-case sample as a full-set estimate.
4. **Mesh320 feasibility:** obtain a successful public development rung on a specified larger-memory machine, with paired error evidence, peak memory and a full-workflow CPU/wall cost. Register its own band and rerun the same recovery calculation.
5. **Cost and authority:** Data Collection supplies cost figures for each complete route, including pending mesh160 work and validation rungs. The owner decides whether to change the reference method and authorizes any spend and eventual v3 band. Until then, both route verdicts remain `INSUFFICIENT_EVIDENCE_FOR_V3_BAND`.

No solver or paid host was run for this comparison. The illustrative sensitivity values above are analysis inputs only and must not enter a reference rule.
