## 2026-10-03 — LP-PROD-A: the research loop runs every tool call of a turn, answers a model's mistakes and rides out provider trouble

**Authority.** OWNER-LAUNCHPAD-PROD-01 (owner, 2026-10-03): the miner front
end is to work with zero friction, as a production-level application, and the
owner approved this work list, including the change to the parallel-call rule
("approve. you launch this now"). The choices below are engineering choices
within that approval. No scientific value, threshold, gate or tolerance, no
spend default, no economic value and no authority boundary changes.

**The defects, checked on main at `4be2642c`.**
1. **One tool call per turn.** Providers return several calls in one turn:
   Graphite live session 1's model did, and the battery tier-2 run's did on
   every sampled turn. Under `PARALLEL_CALLS` (v1) only the first runs. Each
   refused call has to be sent again in a later turn, which spends a model
   call, and three such turns in a row stop the epoch.
2. **A model's mistake raised an exception.** These all raised:
   - arguments that `research_tools._json` refuses: not JSON, `""` for a tool
     that takes no arguments, a duplicate key, NaN, or over 16,384 bytes;
   - a malformed selection. It was checked after its intent file was
     written, so every resume then said "tool dispatch incomplete";
   - a recipe that does not compile, or names no Challenge;
   - a tool call with no `call_id` or `name`.

   The provider's reply is journalled under a fixed identity and replayed on
   resume, so the same exception came back on every resume and the epoch
   could not continue.
3. **Selecting an unpracticed recipe spent the epoch.** The epoch ended
   `SELECTED`. The controller then refused to submit the recipe ("no final
   exam dispatched"), and the agent learned of it only afterwards.
4. **The agent could not see its budget.** It was not told how many model
   calls or trial slots it had left. Also, the loop's trial ceiling did not
   count `run_julia`, although the executor charges it a slot
   (`ResearchMinerTools.call`).
5. **One free-text reminder per epoch.** A long session that wrote free text
   once, did real work, and later wrote free text again was stopped.

**Decision.**
1. **The v2 rule.** `research_agent_policy.PARALLEL_CALLS_V2` has schema
   `carbon.autoresearch.parallel-calls.v2` and rule `EVERY_CALL_RUN_IN_ORDER`.
   Under it, `research_loop.run_epoch`:
   - runs every function call of a turn, one after another, in the model's
     order. The first call keeps the identity `epoch-N-tool-NNN`; later calls
     get `epoch-N-tool-NNN-KK`;
   - journals each call's intent before dispatch and its result after, with
     the same exactly-once and reconciliation semantics as a single call. The
     turn's calls are journalled before any of them runs
     (`<turn>-calls.json`);
   - re-reads the trial count from the ledger before every numerical call
     (practice, `run_python`, `run_julia`), so one turn cannot overspend the
     ceiling;
   - ends the epoch on a selection, a stop or a `requires_reconciliation`
     result. The turn's later calls do not run and are journalled
     (`<turn>-not-run.json`);
   - sends `parallel_tool_calls: true` and has no consecutive-turn stop;
   - adds a short user note before every turn: model calls left, counting
     this turn, and trial slots left (shown only when `start_research_task` is
     offered). With `FINISH_NOTICE_CALLS` (2) calls left, the note tells the
     agent to select or stop now. Each note is journalled
     (`<turn>-status.json`) before its request, so a replay sends a
     byte-identical request;
   - lets any tool call renew the one free-text reminder;
   - lets Carbon's own agent (no role instructions) select only a practiced
     recipe. The test is the controller's own predicate
     (`research_campaign.trial_supports_selection`, imported, not copied). A
     refused selection is answered `selection_not_practiced`, with up to 8
     practiced recipes and their count, and the epoch goes on. A role's caller
     (Graphite) owns what its selection means, so a role is not checked.
2. **Prompts follow the frozen rule.** `prompt_for` and `binding` take the
   rule. Under v2 the prompt states:
   - the v2 rule;
   - the argument bounds: 16,384 bytes of tool arguments and 12,288 bytes of
     `arguments_json`;
   - that `run_julia` spends a slot;
   - the per-turn status note;
   - the selection rule;
   - the renewed reminder.

   `CHALLENGE_PROMPT_V2` is the battery prompt under v2. A historical Burgers
   prompt gains only a v2 section after its own text. Under v1 or no rule,
   every prompt, the operating rules and every policy binding stay byte for
   byte as before. The tests pin their digests from main.
3. **Where v2 is frozen.**
   - New battery campaigns: `battery.campaign.provider_plan`.
   - Every Graphite role: `roles.PARALLEL_RULES`, through both
     `GraphiteProvider._epoch` and `Phase3Provider._epoch`. Every role's
     prompt states the rule, in `_COMMON`, built by
     `every_call_per_turn("session")`.
   - `phase3 run --dry-run`, whose first turn is live session 1's three
     calls. It now runs all three and reports `parallel_calls_run` and
     `parallel_calls_not_run` (`research_loop.parallel_call_counts`), instead
     of `refused_parallel_calls`.

   Burgers campaigns freeze no rule (`research_campaign`, outside this
   slice) and are unchanged.
4. **A model's mistake is answered, under every rule.** Each mistake gets a
   `REJECTED_BEFORE_DISPATCH` tool result with a closed `code`
   (`arguments_invalid`, `selection_invalid`, `candidate_invalid`,
   `selection_not_practiced`), the `field`, the `reason` and the `fix`:
   - `argument_problem` diagnoses only after `_json` has refused. Any value
     the loop accepts is still `_json`'s own, so an intent journalled before
     this change replays unchanged. A deeply nested value is refused, not a
     `RecursionError`.
   - A tool whose schema takes no arguments takes `""`, `null` or no
     arguments as `{}`.
   - A selection is validated before its intent is written. A rejection, a
     stop and a selection dispatch nothing outside the epoch folder, so their
     result is computed before the intent. An intent left without a result
     is recomputed on resume. This also frees an epoch that the old code left
     with a selection intent and no result.
   - A call that leaves the folder keeps exactly-once: an intent without a
     result still stops for reconciliation.
   - A tool call with no `call_id`, or a call that would run with no `name`,
     ends the epoch `STOPPED` with code `tool_call_malformed`, before any call
     of that turn runs.

   These apply under every rule because each one replaces an exception. No
   journalled turn ever completed through any of them, so a v1 or no-rule
   campaign's journalled requests, prompts and plans are unchanged. The
   historical rule's exception for several calls stays: that is the rule.
5. **`run_julia` counts in the trial ceiling under every rule.** This
   enforces the plan's frozen `max_research_trials`; the executor already
   charged the slot.
6. **Provider plumbing.**
   - `research_agent._request_once` accepts `parallel_tool_calls` as a
     Boolean. Before, it had to be `false`.
   - `model_provider.chat_request` puts one turn's calls, and any text before
     them, on one assistant message, as Chat Completions requires. It sends a
     call whose arguments are not one JSON object (none, blank, cut off by
     the output limit, or malformed) as `"{}"`, so an endpoint that parses
     its history cannot refuse the request on the model's own mistake (part
     2). The loop has already answered such a call with a typed result. The
     translation is never journalled, so replays are unaffected.

**Consequences.**
- Every Graphite role's prompt digest changes. A session opened under the old
  prompt refuses to resume (`role_changed`) before any model call, as under
  GRAPHITE-D33, and a registered brief that has not started refuses to start
  (`brief_role_changed`); each has to be opened or registered again. The old
  digests, from main `4be2642c`, are:
  - Planner `sha256:869ed271…29ba`
  - Constructor `sha256:54a29c80…4cbc`
  - Attacker `sha256:f1581bf6…06f1`
  - Optimizer researcher `sha256:dc7b6ee8…fa8c`
  - Reader `sha256:3091b0bc…a245`
  - Writer `sha256:0f1d367a…7d7f`

  The Constructor's is now `sha256:73996c8c…a0f3`.
- A new battery campaign's prompt is `CHALLENGE_PROMPT_V2`
  (`sha256:ea70ce29…e063`).
- A turn with several calls still spends one model call. Each numerical call
  spends its slot as before.
- The status note adds one short user message per turn. It is appended at the
  end, so a cached prefix still holds.

**Alternatives rejected.**
- *Run a turn's calls concurrently.* That would lose the model's order and
  the per-call exactly-once journal.
- *Put the budget into each tool result.* That mixes Carbon's status into a
  tool's own result, and a turn with no call would get none.
- *Apply v2 to campaigns already frozen.* Their replays would change.
- *Apply the mistake fixes under v2 only.* That would keep wedging an older
  campaign's new turns, and no journalled turn changes either way.
- *Cap the calls per turn.* The rule is every call; the provider's
  `max_output_tokens` already bounds how many calls a turn can carry.
- *Require practice for a Graphite selection.* Graphite's evidence is its
  proposal runs, and its caller decides what a selection means.

**Reversal.** Point `provider_plan` and `roles.PARALLEL_RULES` back at
`PARALLEL_CALLS`. A campaign already frozen under v2 keeps v2.

### Part 2: provider resilience

**The defects, checked on this branch before the change** (main `dff575f`
had them at the audit's lines, give or take a few).
1. **A reply the provider ended early stopped the epoch for good.** A reply
   cut off at `max_output_tokens` (Responses `incomplete`, Chat
   `finish_reason: length`, Messages `max_tokens` or `pause_turn`) was
   metered, recorded `FAILED_INFRA` and then raised
   (`research_agent._request_once`, "incomplete provider response"). Every
   resume raised again ("provider outcome uncertain; reconciliation
   required"). The translators did not raise; they mapped the reply to
   `incomplete`, and the agent raised.
2. **Failures that cost nothing were retried twice at most, and some not at
   all.** A rate limit got two resends, each wait capped at 30 s even when
   the provider's Retry-After was longer. A 502 or 503 kept its full
   reservation and stopped the campaign for reconciliation. So did a
   connection refused before anything was sent, and a key file that could
   not be read: both were `UNKNOWN`.
3. **A key or balance rejection replayed forever.** The recorded rejection
   was raised again on every resume, so fixing the key did not help.
4. **A call whose outcome was unknown blocked the campaign forever.** It
   stayed `RESERVED`. Every resume refused it ("no resend"), and a controlled
   campaign refused every later model call ("unknown provider metering;
   reconcile before dispatch", `research_ledger` lines 540-548). The
   reconcile action could not settle it: `reconcile_worker` handles only
   worker operations.

**Decision.**
1. **An early end is a turn.** `request_model(accept_incomplete=True)`
   returns the reply, metered exactly as before. The ledger row is unchanged
   (`FAILED_INFRA`, the metered charge), plus an `incomplete` record:
   `reason` (`max_output_tokens`, the provider's own stop reason, or
   `unknown`), `output_tokens` and `max_output_tokens`. The translators add
   the Responses API's `incomplete_details.reason`. The research loop is the
   one caller that accepts. Every other caller (Graphite's closed tasks and
   card triage) keeps its historical refusal, on replay too. In the loop:
   - the turn spends one model call;
   - each call the reply finished runs. A call the provider marks
     unfinished, and the reply's last item when it is a call not marked
     completed, is answered `call_truncated` (a new closed refusal code) and
     does not run;
   - a user note, journalled once in `<turn>-truncated.json`
     (`carbon.autoresearch.turn-truncated.v1`), says how the reply ended and
     asks the model to continue. After the output limit it says "cut off at
     its limit of N output tokens" and asks for shorter replies;
   - a reply cut off before any call is not a choice to stop, and spends no
     free-text reminder;
   - an early end recorded by the old code (no `incomplete` field) now
     resumes the same way.
2. **Failures that cost nothing are retried with backoff.** These are
   `model_provider.RETRY_SAFE`:
   - a rate limit or overload (as before);
   - a 502, 503 or 529 whose body carries no usage object (new outcome
     `server_unavailable`). This is the reading the owner approved in the
     work list; the `ErrorSemantics` basis texts record it, still not
     invoice-verified. A 5xx that reports usage, and 500 and 504, stay
     uncertain. *2026-10-03, closed by OWNER-LAUNCHPAD-PROD-02 (answer 3,
     "yes"): booked at zero and retried, as recorded here;*
   - a connection refused, or a name that did not resolve, raised from the
     connect before any request byte (new outcome `unreachable`, raised as
     `ProviderUnreachable`, an `OSError`). Any other connection failure stays
     `unknown`.

   Each attempt is its own operation, counted with no token charge, under the
   next identity (`-rlN`) and its own reservation, so the ledger's ceilings
   admit every attempt. The waits (`research_agent.retry_wait`) are:
   - exponential backoff, 2 s doubling to at most 60 s, with equal jitter
     (half fixed, half random);
   - never shorter than Retry-After;
   - at most `MAX_AUTOMATIC_RETRIES` (6) retries and `MAX_RETRY_WAIT_SECONDS`
     (300 s) of waiting per call. A Retry-After longer than the wait left
     ends the call's retries at once rather than being cut short.

   These bound only wall time and the attempt count; no money is spent on a
   retried failure.
3. **A key or balance problem is resumable.** It raises `ProviderCallFailed`
   at once, with no retry. A later call (a resume) passes the recorded
   rejection and sends the request under the next identity. The same holds
   for retries that ran out. A context-limit or invalid-request rejection
   still replays: the same request would get the same answer. A key file
   Carbon cannot read is now `CredentialUnavailable`, a credential failure
   found before anything is sent, and no longer an unknown outcome.
   `ProviderCallFailed` adds `resumable`, `requires_settlement` and
   `report()`: a closed code `provider_<outcome>` and a next step. It never
   contains provider text.
4. **A call whose outcome is unknown is settled explicitly.** The no-resend
   rule stands: nothing settles a call automatically, and nothing is resent
   while it is unsettled. What is known is journalled beside the call
   (`uncertain.json`, `carbon.autoresearch.provider-uncertain.v1`):
   `transport_outcome_unknown` (with the typed failure), `usage_unavailable`,
   `usage_beyond_bounds`, `usage_exceeds_reservation`, `model_mismatch` or
   `charge_exceeds_reservation` (part 3 added the two usage reasons). The
   reconcile action calls `research_agent.settle_uncertain_calls` (or
   `settle_uncertain_call` for one call). Each settlement:
   - is journalled beside the call (`settlement.json`,
     `carbon.autoresearch.provider-settlement.v1`) before the ledger books
     it;
   - finishes the operation `FAILED_INFRA`, with the settlement as its result
     and `retry_dispatched: false`;
   - is idempotent: settling again returns the same settlement.

   The next `request_model` of that turn passes the settled identity and
   sends the same request under the next one, with its own reservation. A
   settlement is refused, and the operation left unchanged, with a closed
   code (`SETTLEMENT_REFUSALS`): `operation_unavailable`,
   `not_a_provider_call`, `not_uncertain`, `request_changed`,
   `charge_exceeds_reservation`, and since part 3
   `usage_exceeds_reservation`, `call_in_flight` and `control_fenced`.
   `uncertain_calls` lists what a settlement would book, its caveat, and why
   one would be refused.
5. **The accounting rule (corrected in part 3).** A settled call is booked
   at its full reservation: the money reservation, the attempt and the
   reserved bytes. The money reservation is the most the request can cost at
   the selection's prices within the token limits it reserved (all input at
   the input price, plus the output cap at the output price). It is not a
   bound on what a provider can bill: a provider can report usage beyond the
   request's limits (a chat provider may count reasoning outside its output
   cap), or a charge of its own above it. So a settlement is refused, never
   booked under the provider's figures, when:
   - the provider reported a charge above the reservation
     (`charge_exceeds_reservation`), from the journal or from the retained
     reply's `x_engy.charged_micro`;
   - the reply's usage, at the selection's prices, costs more than the
     reservation (`usage_exceeds_reservation`), from the journal or, when the
     journal is missing, whenever the retained reply reports more output
     tokens than the retained request reserved.

   Such a call has to be reconciled against the provider's own usage record;
   the ledger cannot book more than a reservation. Usage beyond the limits
   whose charge still fits (`usage_beyond_bounds`) is booked at the
   reservation, which covers it. A call answered by another model
   (`model_mismatch`) is booked at the selected model's reservation with a
   recorded caveat (`MODEL_CAVEAT`): that model's price is unknown to
   Carbon, so the booking is not a proven upper bound. An unpriced selection
   books the attempt and bytes; its money stays unmetered, as before.
   `provider_turns` lists a turn's settled calls under `settled`, with the
   basis "outcome unknown; full reservation booked by settlement". A turn
   with no settlement, and no early end, has exactly the record it had
   before.
6. **The default output cap stays 2,048 tokens.** It is a spend default; see
   the owner input below. With decision 1, hitting it no longer stops an
   epoch.

**Consequences.**
- A resumed campaign that an incomplete reply, a key rejection or exhausted
  retries had stopped now continues, spending model calls. No journalled
  turn, prompt, plan or digest changes.
- A failed 502 or 503 now books nothing for that attempt; before, it booked
  the full reservation and stopped. A miner whose provider bills such a reply
  would see Carbon under-count it. This is the work list's reading; it is not
  invoice-verified.
- Retries spend `provider_attempts` and wall time. Under a sustained rate
  limit, one call can make up to 7 attempts in one run, and a resume makes
  more. A run with an attempt ceiling (a development grant, a Graphite run)
  reaches it sooner.
- In Graphite's card triage test, a scripted 503 now reaches its unknown
  outcome through the retry (`test_graphite_method_cards`, unchanged and
  passing).
- The loop records new journals: `<turn>-truncated.json` in the epoch
  folder, and `uncertain.json` and `settlement.json` beside each model call.

**Alternatives rejected.**
- *Record an early end `SUCCEEDED`.* A caller that does not accept one would
  then replay it as a success. The row stays as it always was, and the
  `incomplete` record says how the reply ended.
- *Run every call of a reply that ended early.* Its last call may be cut
  mid-arguments; a `run_python` with half a program would spend a trial
  slot on nothing.
- *Settle automatically at the end of a run.* That would resend a possibly
  charged call without anyone deciding to. Settlement stays an explicit
  reconcile action.
- *Book a settled call at its estimate or at zero.* That could under-count
  spend.
- *Treat 500 and 504 as retry-safe.* The request may have been processed;
  they stay uncertain.
- *Retry a key rejection at once.* It fails again until the miner acts.

**Reversal.**
- Drop `accept_incomplete=True` from `run_epoch`; the old refusal returns.
- Remove `unavailable_statuses` from the error semantics: 502 and 503 go back
  to uncertain.
- Set `MAX_AUTOMATIC_RETRIES` to 2.
- Remove the resumable pass in `_rejected`.

Recorded rows stay readable either way: a settled call has a distinct
result, and a reply that ended early is the row it always was.

  - settlement after a timeout, a 500, missing usage and a different model:

**Owner input still open (part 2).** Whether to raise the default output cap
(`model_provider.DEFAULT_SETTINGS.max_output_tokens`, 2,048 tokens) is a spend
default, so it is the owner's. The evidence:
- **Reasoning counts against the cap.** OpenAI's output price includes
  reasoning tokens (`GPT5_MINI_PRICING`), and the default effort is `low`.
- **A stated argument cannot fit.** Under v2 the agent is told it may send
  16,384 bytes of tool arguments. At the roughly 4.2 bytes per token measured
  on a live request on 2026-10-03 (lesson
  `2026-10-03-planner-run-2-output-truncated`), that is about 3,900 tokens,
  so one call at the stated limit cannot fit in a 2,048-token reply.
- **A real reply was cut off.** The Graphite level planner's second live
  reply ran past its 8,192-token output limit (same lesson).
  GRAPHITE-GRANT-PLANNER-02 then sized that role for a medium-effort reply,
  at 32,768 tokens.
- **Cost.** Each extra output token raises the per-call reservation by the
  model's output price: about USD 0.0123 for 8,192 tokens on the pinned
  `gpt-5-mini` (USD 0.0205 to 0.0328), and about USD 0.0006 on
  `deepseek-v4-flash-0731`. Where the provider reports no charge (Engy
  without `x_engy.charged_micro`), the full reservation is what is booked.

A miner can already set `max_output_tokens` per selection (256 to 131,072).

*2026-10-03, closed by OWNER-LAUNCHPAD-PROD-02 (answer 1, "why would we limit
an agents output tokens? ... It's their economics, compute, and choice!"):*
no Carbon-imposed output cap. A new plan's default is the selected model's
own maximum output, and only a cap the miner sets binds; see the last section
below. Decision 6's 2,048 stays the historical default every earlier plan
recorded.

### Part 3: repairs after the independent review

**The defects the review found in parts 1 and 2, each checked against the
code.**
1. **A settlement could book less than the provider's own usage implied.**
   Usage beyond the reserved token limits was journalled `usage_unavailable`,
   like missing usage, and settled at the reservation. A reply reporting 100
   input and 50,000 output tokens settled at 20,480,000 nanodollars although
   its usage meters 100,025,000. The part 2 accounting sentence ("it cannot
   have charged more than the reservation") was false on that path, and on
   `model_mismatch`, whose price is unknown.
2. **Replies cut off in a row had no bound.** A reply ended early with no
   call run went on with no counter, under every rule. A model that is
   always cut off, or a provider whose stop reason is never `completed`,
   would spend all 48 model calls of an epoch for nothing, where before it
   spent one and stopped.
3. **Settlement had no fence of its own.** It checked neither the owner lock
   nor the control generation, and `uncertain_calls` listed a call still in
   flight. A settlement made while a call ran would book it, the call's own
   finish would conflict, and the next resume would send it again: a second
   paid send. Only the caller's discipline (slice C's reconcile action under
   the owner lock) prevented that.
4. Smaller ones: a stop reason that is not a string raised `TypeError` before
   the call was booked; the unresolved outcomes were plain `ValueError`s with
   no report; an Engy error body carrying `x_engy` but no `usage` was booked
   at zero; and OWNER-LAUNCHPAD-PROD-01 said every earlier campaign replays
   byte-identically, which is not so for Graphite.

**Decision.**
1. **Usage is classified when it cannot be booked.** `_request_once` reads
   usage that `usage_cost` refuses (`_beyond_bounds`). Whole token counts
   beyond the reserved limits are priced at the selection's prices, every
   input token at the higher of its uncached and cached price, or at the
   provider's own reported charge where the adapter reports one. Above the
   money reservation, the journal says `usage_exceeds_reservation`;
   otherwise `usage_beyond_bounds`. Either way the journal records the
   charge (`metered_nanodollars`). Anything else stays `usage_unavailable`.
2. **The settlement reads the retained reply as well as the journal**
   (`_figures_refusal`), because the journal is written best effort and a
   call left unresolved before it existed has none. It refuses
   `charge_exceeds_reservation` on a reported charge above the reservation.
   It refuses `usage_exceeds_reservation` when the reply reports more output
   tokens than the retained request reserved, unless the call's own journal
   shows that the charge fits (`usage_beyond_bounds` with
   `metered_nanodollars` within the reservation). A call with no money
   reservation is not refused on its figures: it books no money.
3. **A different model is booked with a caveat.** `model_mismatch` settles at
   the selected model's reservation, and the settlement (with its
   `settlement.json`) and `uncertain_calls` carry `caveat` (`MODEL_CAVEAT`):
   that model's price is
   unknown, so the booking is not a proven upper bound; check the provider's
   own usage record. Without a journal, the caveat is read from the retained
   reply's model. The alternative, refusing, would leave the campaign stopped
   with no way forward; the choice is listed for the owner to confirm.
   *2026-10-03, closed by OWNER-LAUNCHPAD-PROD-02 (answer 2, "don't care"):
   the booking stands as recorded here, with its caveat.*
4. **Two replies in a row that run nothing stop the epoch.** A reply ended
   early in which no call that runs was complete (it had none, or each was
   cut) is counted. The first gets the note, which now says that the next
   such reply stops the run. The second ends the epoch `STOPPED` with code
   `replies_truncated` (`MAX_TRUNCATED_TURNS`, 2), its turns and how the
   reply ended, before anything of it runs. A reply in which any call ran,
   or any completed reply, resets the count. It replays identically.
5. **Settlement is fenced twice.**
   - *A call in flight is never settled.* Every model call holds the
     campaign's provider-call lease (`provider-calls.lock`, an OS file lock
     beside the ledger) shared, from before its reservation until it is
     booked or left unresolved; a backoff wait holds none. A settlement takes
     it exclusively without waiting and is refused `call_in_flight` while any
     call, in this process or another, holds it. The OS releases a lease when
     its holder exits. A host without POSIX file locks cannot show that no
     call is in flight, so it never settles.
   - *Only the reconcile action books a settlement.*
     `CampaignLedger.assert_reconciling` requires, for a controlled campaign,
     the retained owner under the live control generation
     (`retained_owner`) and the campaign observed `RECONCILING`, which
     `CampaignControl.acquire` sets under the owner lock and a run's first
     dispatch leaves. It runs before the settlement is journalled, and again
     inside `finish(reconciling=True)`, in the booking's own transaction, as
     `_reserve` asserts dispatch control. A refusal is `control_fenced`. The
     development CLI's own campaign has no control to prove; the lease still
     applies.
6. **Typed unresolved outcomes.** `ProviderCallUnresolved`, a `ValueError`
   with the message it always had (so a caller that handled one handles this
   unchanged), carries `reason`, `requires_settlement` and `report()`, a
   closed code `provider_<reason>` and a next step
   (`UNRESOLVED_NEXT_STEPS`). It is deliberately not a `ProviderCallFailed`:
   Graphite's closed tasks and triage, outside this slice, treat that one
   differently.
7. **Untrusted stop reasons.** A stop reason that is not a string is
   `unknown` in `incomplete_reply` and in the translators, never a lookup
   that raises.
8. **A provider charge in an error body counts as usage.** A 502, 503 or 529
   body carrying `x_engy` is read like one carrying `usage`: it may have been
   billed, so it stays `transient_server` with its reservation.

**Consequences.**
- A campaign's root gains `provider-calls.lock`, an empty lock file.
- A settlement during a run, from a stale holder, or while any call is in
  flight is refused, and the call stays `RESERVED`.
- A call whose usage costs more than its reservation stays unresolved until
  it is reconciled by hand against the provider's record; Carbon has no tool
  for that yet.
- A model that keeps being cut off now stops after two model calls, not 48.
- A resume does not wait out a Retry-After that ended an earlier call's
  retries: the next call is sent at once. If the provider still refuses it,
  the new refusal's Retry-After is honoured, and the refused attempt costs
  nothing. (Review nit, documented rather than changed.)

**Alternatives rejected.**
- *Refuse every settlement of usage beyond the limits.* A chat provider that
  counts reasoning outside its cap would stop every such campaign for good,
  though the reservation covers the charge.
- *Book over-limit usage at its metered charge.* The ledger cannot book more
  than a reservation, and changing what `usage_cost` admits widens the
  accounting change.
- *Write the call's prices beside every request, so a settlement can price
  any retained usage.* One more file per call; the journal plus the
  output-token check cover the cases found. Input tokens beyond the limit
  are checked only through the journal: admission holds back 4,096 tokens
  for the reply, so a provider would have to report that much overhead.
- *Fence settlement by the owner lock alone.* The lock guards the caller's
  discipline, not the call: a call left running by an earlier holder in the
  same process would still be settled.
- *Make the unresolved outcomes `ProviderCallFailed`.* That would change how
  Graphite's closed tasks and triage, outside this slice, stop on them.

**Reversal.** Drop `MAX_TRUNCATED_TURNS`'s check from `run_epoch`; drop the
lease and the `reconciling` fence from settlement; add `model_mismatch` to the
settlement refusals to refuse instead of booking with a caveat. Recorded rows
stay readable.

**Tests (part 3).**
- `tests/cpu/test_provider_resilience.py`: usage costing more than the
  reservation is refused, with and without the journal; usage beyond the
  limits that fits is settled with its charge journalled, and refused without
  the journal; a reply without usage is typed and reported; a different model
  is booked with the caveat, also read from the retained reply; the run's own
  holder and a stale holder are refused, in `finish` too, and the current
  holder settles; a call in flight is refused by one settlement, the batch
  and the listing, then settles once it has ended; a stop reason that is not
  a string is `unknown`, booked, and translated. The product-campaign test
  now settles as the reconcile action does (after `CampaignControl.acquire`)
  and shows the running holder refused.
- `tests/cpu/test_research_loop_resilience.py`: replies cut off in a row stop
  the epoch under every rule (no call, a cut call, a non-standard stop
  reason), with the warning note and an identical replay; a reply whose call
  ran resets the count.
- `tests/cpu/test_model_provider.py`: an error body carrying `x_engy` is
  `transient_server`.

**Unchanged.** Graphite proposes; Carbon's verifier decides (invariants 7.9
and 7.10). A paid call whose outcome is unknown is never resent blind. No live
session was run and nothing was spent. None of this is scientific, security
or production qualification.

### 2026-10-03 — Closed by OWNER-LAUNCHPAD-PROD-02: no Carbon-imposed output cap for a new plan

**Authority.** OWNER-LAUNCHPAD-PROD-02, decision 1 (the owner, answer 1:
"why would we limit an agents output tokens? Don't we want them running the
best possible agents? It's their economics, compute, and choice!"). The
choices below are engineering choices implementing it. No scientific value,
gate or threshold changes; the economics are the miner's own ceilings, which
are unchanged.

**Decision.**
1. **A new plan's output cap defaults to the selected model's own maximum
   output** (`model_provider.OUTPUT_DEFAULT_V2`,
   `carbon.model-selection.output-default.v2`). `output_maximum` reads it in
   this order:
   - the model's own documented maximum (`ProviderAdapter.output_maxima`);
   - otherwise the provider's documented maximum for the models it serves
     (`ProviderAdapter.output_maximum`);
   - otherwise none is known, and Carbon does not guess one. The
     conservative historical cap (2,048) is kept until the miner sets their
     own: a cap above a model's real maximum is refused by its provider as an
     invalid request, which replays and stops the campaign.

   Never outside the selectable bounds (`OUTPUT_TOKEN_BOUNDS`, 256 to
   131,072).
2. **What Carbon records, sourced and dated like a price** (`OutputMaximum`).
   Nothing in `model_provider` recorded a maximum before, so the two Carbon
   lists were read from their providers on 2026-10-03:
   - `gpt-5-mini-2025-08-07` (the pinned model): 128,000 output tokens,
     OpenAI's model page;
   - the Engy ladder (`engy-anthropic`, `engy-chat`): Engy's public list
     states no output maximum apart from each model's context
     (`max_model_len` equals `context_length`, 262,144 or more), which leaves
     more than 131,072 after the default 65,536-token input, so the default
     is Carbon's highest cap, 131,072.

   Every other model (the Anthropic adapter, Chutes, the OpenAI-compatible
   adapters, an unlisted OpenAI model) has no recorded maximum and keeps
   2,048 by default.
3. **Only a cap the miner sets binds.** A `max_output_tokens` in the
   launch's `model_settings` (or a CLI `model_selection`) overrides the
   default under either rule.
4. **Where the new default applies: a new product plan.** The miner's own
   campaign, on the miner's own budget:
   - battery's `prepare_battery` and Burgers' `campaign_selection`, for a
     campaign not yet frozen whose arguments carry the launch's product
     (`research_campaign.new_plan_output_default`);
   - the Launchpad's launch choice (`_launch_choice`), so what a launch
     validates is what the campaign builds.

   `select()` without it is unchanged: the pinned default
   (`DEFAULT_SETTINGS` and `DEFAULT_SELECTION` keep 2,048 and their manifest
   block), every re-validation of a record, Graphite's roles and closed
   tasks, the battery tier scripts, and a campaign admitted by a development
   grant, whose ceilings were sized for the historical default.
5. **Earlier plans keep what they recorded.** A plan records its selection's
   settings (or, for the pinned default, records none and resolves to
   `DEFAULT_SETTINGS`), so it resolves to the same record and replays byte
   for byte. A resume that supplies the same choice without a cap names the
   frozen one under either default (`resolve_selection`); a different cap is
   still refused.
6. **Reservation and metering are unchanged in kind.** Each call reserves
   its maximum (all input at the input price, plus the cap at the output
   price) against the miner's own ceilings before dispatch, and is settled
   from the provider's charge or metered usage.

**Consequences.**
- Per-call reservations are larger. On `gpt-5-mini` the reservation goes from
  USD 0.0205 to about USD 0.272 (65,536 input and 128,000 output tokens); on
  `deepseek-v4-flash-0731` from about USD 0.0031 to about USD 0.0147. A money
  ceiling below one reservation refuses that call before dispatch
  (`miner budget: provider_nanodollars`); the miner sets a cap or a larger
  ceiling.
- Where a provider reports no charge (Engy without `x_engy.charged_micro`),
  the full reservation is booked, so such a call books more at the larger
  cap.
- A new plan on the pinned model is no longer the historical default: it
  records its selection (`model_selection`) and runs through
  `SelectionTransport`.
- The doors' `model_settings` description says the default.

**Reversal.** Drop `output_default` from the new-plan callers; new plans then
take 2,048 again. Plans frozen under either rule keep their recorded cap.

**Tests.** `tests/cpu/test_lp_prod_output_default.py`: a new plan reserves
at the model maximum, is sent with it and is metered at usage; a miner cap
binds, and a ceiling below the maximum reservation refuses the uncapped call
and admits the capped one; an old plan (pinned and recorded) resolves to its
recorded record and a resume without a cap is accepted; a model with no
documented maximum keeps 2,048; only a new product plan takes the default.
`tests/cpu/test_launch_model_selection.py`
(`test_a_chosen_output_cap_reaches_the_campaign_and_its_record`): its
specimen, a launch without settings, now takes the model's maximum (131,072
on Engy), not 2,048. `tests/service/test_launchpad_production_journey.py`:
its battery fixture now freezes and reads the plan's selection as
`prepare_battery` does, its budget is sized in the new reservation, and
scenario 5 settles the unknown call at the new plan's reservation, above the
historical one. `tests/cpu/test_agentless_campaign_needs_no_provider_key.py`:
the specimen accepts the selection's transport, built from the same key
file, since a new plan on the pinned model is no longer the historical
