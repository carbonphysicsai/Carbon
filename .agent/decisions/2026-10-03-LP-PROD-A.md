## 2026-10-03 — LP-PROD-A: the research loop runs every tool call of a turn, answers a model's mistakes and rides out provider trouble

**Authority.** OWNER-LAUNCHPAD-PROD-01 (owner, 2026-10-03): the miner front
end is to work with zero friction, as a production-level application, and the
owner approved this work list, including the change to the parallel-call rule
("approve. you launch this now"). The choices below are engineering choices
within that approval. No scientific value, threshold, gate or tolerance, no
spend default, no economic value and no authority boundary changes.

**The defects, checked on main at `4be2642c`.**
1. **One tool call per turn.** Providers return several calls in one turn:
   Graphite live session 1's model did, and the battery tier-2 run's did on
   every sampled turn. Under `PARALLEL_CALLS` (v1) only the first runs. Each
   refused call has to be sent again in a later turn, which spends a model
   call, and three such turns in a row stop the epoch.
2. **A model's mistake raised an exception.** These all raised:
   - arguments that `research_tools._json` refuses: not JSON, `""` for a tool
     that takes no arguments, a duplicate key, NaN, or over 16,384 bytes;
   - a malformed selection. It was checked after its intent file was
     written, so every resume then said "tool dispatch incomplete";
   - a recipe that does not compile, or names no Challenge;
   - a tool call with no `call_id` or `name`.

   The provider's reply is journalled under a fixed identity and replayed on
   resume, so the same exception came back on every resume and the epoch
   could not continue.
3. **Selecting an unpracticed recipe spent the epoch.** The epoch ended
   `SELECTED`. The controller then refused to submit the recipe ("no final
   exam dispatched"), and the agent learned of it only afterwards.
4. **The agent could not see its budget.** It was not told how many model
   calls or trial slots it had left. Also, the loop's trial ceiling did not
   count `run_julia`, although the executor charges it a slot
   (`ResearchMinerTools.call`).
5. **One free-text reminder per epoch.** A long session that wrote free text
   once, did real work, and later wrote free text again was stopped.

**Decision.**
1. **The v2 rule.** `research_agent_policy.PARALLEL_CALLS_V2` has schema
   `carbon.autoresearch.parallel-calls.v2` and rule `EVERY_CALL_RUN_IN_ORDER`.
   Under it, `research_loop.run_epoch`:
   - runs every function call of a turn, one after another, in the model's
     order. The first call keeps the identity `epoch-N-tool-NNN`; later calls
     get `epoch-N-tool-NNN-KK`;
   - journals each call's intent before dispatch and its result after, with
     the same exactly-once and reconciliation semantics as a single call. The
     turn's calls are journalled before any of them runs
     (`<turn>-calls.json`);
   - re-reads the trial count from the ledger before every numerical call
     (practice, `run_python`, `run_julia`), so one turn cannot overspend the
     ceiling;
   - ends the epoch on a selection, a stop or a `requires_reconciliation`
     result. The turn's later calls do not run and are journalled
     (`<turn>-not-run.json`);
   - sends `parallel_tool_calls: true` and has no consecutive-turn stop;
   - adds a short user note before every turn: model calls left, counting
     this turn, and trial slots left (shown only when `start_research_task` is
     offered). With `FINISH_NOTICE_CALLS` (2) calls left, the note tells the
     agent to select or stop now. Each note is journalled
     (`<turn>-status.json`) before its request, so a replay sends a
     byte-identical request;
   - lets any tool call renew the one free-text reminder;
   - lets Carbon's own agent (no role instructions) select only a practiced
     recipe. The test is the controller's own predicate
     (`research_campaign.trial_supports_selection`, imported, not copied). A
     refused selection is answered `selection_not_practiced`, with up to 8
     practiced recipes and their count, and the epoch goes on. A role's caller
     (Graphite) owns what its selection means, so a role is not checked.
2. **Prompts follow the frozen rule.** `prompt_for` and `binding` take the
   rule. Under v2 the prompt states:
   - the v2 rule;
   - the argument bounds: 16,384 bytes of tool arguments and 12,288 bytes of
     `arguments_json`;
   - that `run_julia` spends a slot;
   - the per-turn status note;
   - the selection rule;
   - the renewed reminder.

   `CHALLENGE_PROMPT_V2` is the battery prompt under v2. A historical Burgers
   prompt gains only a v2 section after its own text. Under v1 or no rule,
   every prompt, the operating rules and every policy binding stay byte for
   byte as before. The tests pin their digests from main.
3. **Where v2 is frozen.**
   - New battery campaigns: `battery.campaign.provider_plan`.
   - Every Graphite role: `roles.PARALLEL_RULES`, through both
     `GraphiteProvider._epoch` and `Phase3Provider._epoch`. Every role's
     prompt states the rule, in `_COMMON`, built by
     `every_call_per_turn("session")`.
   - `phase3 run --dry-run`, whose first turn is live session 1's three
     calls. It now runs all three and reports `parallel_calls_run` and
     `parallel_calls_not_run` (`research_loop.parallel_call_counts`), instead
     of `refused_parallel_calls`.

   Burgers campaigns freeze no rule (`research_campaign`, outside this
   slice) and are unchanged.
4. **A model's mistake is answered, under every rule.** Each mistake gets a
   `REJECTED_BEFORE_DISPATCH` tool result with a closed `code`
   (`arguments_invalid`, `selection_invalid`, `candidate_invalid`,
   `selection_not_practiced`), the `field`, the `reason` and the `fix`:
   - `argument_problem` diagnoses only after `_json` has refused. Any value
     the loop accepts is still `_json`'s own, so an intent journalled before
     this change replays unchanged. A deeply nested value is refused, not a
     `RecursionError`.
   - A tool whose schema takes no arguments takes `""`, `null` or no
     arguments as `{}`.
   - A selection is validated before its intent is written. A rejection, a
     stop and a selection dispatch nothing outside the epoch folder, so their
     result is computed before the intent. An intent left without a result
     is recomputed on resume. This also frees an epoch that the old code left
     with a selection intent and no result.
   - A call that leaves the folder keeps exactly-once: an intent without a
     result still stops for reconciliation.
   - A tool call with no `call_id`, or a call that would run with no `name`,
     ends the epoch `STOPPED` with code `tool_call_malformed`, before any call
     of that turn runs.

   These apply under every rule because each one replaces an exception. No
   journalled turn ever completed through any of them, so a v1 or no-rule
   campaign's journalled requests, prompts and plans are unchanged. The
   historical rule's exception for several calls stays: that is the rule.
5. **`run_julia` counts in the trial ceiling under every rule.** This
   enforces the plan's frozen `max_research_trials`; the executor already
   charged the slot.
6. **Provider plumbing.**
   - `research_agent._request_once` accepts `parallel_tool_calls` as a
     Boolean. Before, it had to be `false`.
   - `model_provider.chat_request` puts one turn's calls, and any text before
     them, on one assistant message, as Chat Completions requires. It sends a
     call whose arguments are not one JSON object (none, blank, cut off by
     the output limit, or malformed) as `"{}"`, so an endpoint that parses
     its history cannot refuse the request on the model's own mistake (part
     2). The loop has already answered such a call with a typed result. The
     translation is never journalled, so replays are unaffected.

**Consequences.**
- Every Graphite role's prompt digest changes. A session opened under the old
  prompt refuses to resume (`role_changed`) before any model call, as under
  GRAPHITE-D33. The old digests, from main `4be2642c`, are:
  - Planner `sha256:869ed271…29ba`
  - Constructor `sha256:54a29c80…4cbc`
  - Attacker `sha256:f1581bf6…06f1`
  - Optimizer researcher `sha256:dc7b6ee8…fa8c`
  - Reader `sha256:3091b0bc…a245`
  - Writer `sha256:0f1d367a…7d7f`

  The Constructor's is now `sha256:73996c8c…a0f3`.
- A new battery campaign's prompt is `CHALLENGE_PROMPT_V2`
  (`sha256:ea70ce29…e063`).
- A turn with several calls still spends one model call. Each numerical call
  spends its slot as before.
- The status note adds one short user message per turn. It is appended at the
  end, so a cached prefix still holds.

**Alternatives rejected.**
- *Run a turn's calls concurrently.* That would lose the model's order and
  the per-call exactly-once journal.
- *Put the budget into each tool result.* That mixes Carbon's status into a
  tool's own result, and a turn with no call would get none.
- *Apply v2 to campaigns already frozen.* Their replays would change.
- *Apply the mistake fixes under v2 only.* That would keep wedging an older
  campaign's new turns, and no journalled turn changes either way.
- *Cap the calls per turn.* The rule is every call; the provider's
  `max_output_tokens` already bounds how many calls a turn can carry.
- *Require practice for a Graphite selection.* Graphite's evidence is its
  proposal runs, and its caller decides what a selection means.

**Reversal.** Point `provider_plan` and `roles.PARALLEL_RULES` back at
`PARALLEL_CALLS`. A campaign already frozen under v2 keeps v2.

**Tests.**

  - the status note and its notice, replayed byte-identically, and none

### Part 2: provider resilience

**The defects, checked on this branch before the change** (main `dff575f`
had them at the audit's lines, give or take a few).
1. **A reply the provider ended early stopped the epoch for good.** A reply
   cut off at `max_output_tokens` (Responses `incomplete`, Chat
   `finish_reason: length`, Messages `max_tokens` or `pause_turn`) was
   metered, recorded `FAILED_INFRA` and then raised
   (`research_agent._request_once`, "incomplete provider response"). Every
   resume raised again ("provider outcome uncertain; reconciliation
   required"). The translators did not raise; they mapped the reply to
   `incomplete`, and the agent raised.
2. **Failures that cost nothing were retried twice at most, and some not at
   all.** A rate limit got two resends, each wait capped at 30 s even when
   the provider's Retry-After was longer. A 502 or 503 kept its full
   reservation and stopped the campaign for reconciliation. So did a
   connection refused before anything was sent, and a key file that could
   not be read: both were `UNKNOWN`.
3. **A key or balance rejection replayed forever.** The recorded rejection
   was raised again on every resume, so fixing the key did not help.
4. **A call whose outcome was unknown blocked the campaign forever.** It
   stayed `RESERVED`. Every resume refused it ("no resend"), and a controlled
   campaign refused every later model call ("unknown provider metering;
   reconcile before dispatch", `research_ledger` lines 540-548). The
   reconcile action could not settle it: `reconcile_worker` handles only
   worker operations.

**Decision.**
1. **An early end is a turn.** `request_model(accept_incomplete=True)`
   returns the reply, metered exactly as before. The ledger row is unchanged
   (`FAILED_INFRA`, the metered charge), plus an `incomplete` record:
   `reason` (`max_output_tokens`, the provider's own stop reason, or
   `unknown`), `output_tokens` and `max_output_tokens`. The translators add
   the Responses API's `incomplete_details.reason`. The research loop is the
   one caller that accepts. Every other caller (Graphite's closed tasks and
   card triage) keeps its historical refusal, on replay too. In the loop:
   - the turn spends one model call;
   - each call the reply finished runs. A call the provider marks
     unfinished, and the reply's last item when it is a call not marked
     completed, is answered `call_truncated` (a new closed refusal code) and
     does not run;
   - a user note, journalled once in `<turn>-truncated.json`
     (`carbon.autoresearch.turn-truncated.v1`), says how the reply ended and
     asks the model to continue. After the output limit it says "cut off at
     its limit of N output tokens" and asks for shorter replies;
   - a reply cut off before any call is not a choice to stop, and spends no
     free-text reminder;
   - an early end recorded by the old code (no `incomplete` field) now
     resumes the same way.
2. **Failures that cost nothing are retried with backoff.** These are
   `model_provider.RETRY_SAFE`:
   - a rate limit or overload (as before);
   - a 502, 503 or 529 whose body carries no usage object (new outcome
     `server_unavailable`). This is the reading the owner approved in the
     work list; the `ErrorSemantics` basis texts record it, still not
     invoice-verified. A 5xx that reports usage, and 500 and 504, stay
     uncertain;
   - a connection refused, or a name that did not resolve, raised from the
     connect before any request byte (new outcome `unreachable`, raised as
     `ProviderUnreachable`, an `OSError`). Any other connection failure stays
     `unknown`.

   Each attempt is its own operation, counted with no token charge, under the
   next identity (`-rlN`) and its own reservation, so the ledger's ceilings
   admit every attempt. The waits (`research_agent.retry_wait`) are:
   - exponential backoff, 2 s doubling to at most 60 s, with equal jitter
     (half fixed, half random);
   - never shorter than Retry-After;
   - at most `MAX_AUTOMATIC_RETRIES` (6) retries and `MAX_RETRY_WAIT_SECONDS`
     (300 s) of waiting per call. A Retry-After longer than the wait left
     ends the call's retries at once rather than being cut short.

   These bound only wall time and the attempt count; no money is spent on a
   retried failure.
3. **A key or balance problem is resumable.** It raises `ProviderCallFailed`
   at once, with no retry. A later call (a resume) passes the recorded
   rejection and sends the request under the next identity. The same holds
   for retries that ran out. A context-limit or invalid-request rejection
   still replays: the same request would get the same answer. A key file
   Carbon cannot read is now `CredentialUnavailable`, a credential failure
   found before anything is sent, and no longer an unknown outcome.
   `ProviderCallFailed` adds `resumable`, `requires_settlement` and
   `report()`: a closed code `provider_<outcome>` and a next step. It never
   contains provider text.
4. **A call whose outcome is unknown is settled explicitly.** The no-resend
   rule stands: nothing settles a call automatically, and nothing is resent
   while it is unsettled. What is known is journalled beside the call
   (`uncertain.json`, `carbon.autoresearch.provider-uncertain.v1`):
   `transport_outcome_unknown` (with the typed failure), `usage_unavailable`,
   `model_mismatch` or `charge_exceeds_reservation`. The reconcile action
   calls `research_agent.settle_uncertain_calls` (or `settle_uncertain_call`
   for one call). Each settlement:
   - is journalled beside the call (`settlement.json`,
     `carbon.autoresearch.provider-settlement.v1`) before the ledger books
     it;
   - finishes the operation `FAILED_INFRA`, with the settlement as its result
     and `retry_dispatched: false`;
   - is idempotent: settling again returns the same settlement.

   The next `request_model` of that turn passes the settled identity and
   sends the same request under the next one, with its own reservation. A
   settlement is refused, and the operation left unchanged, with a closed
   code (`SETTLEMENT_REFUSALS`): `operation_unavailable`,
   `not_a_provider_call`, `not_uncertain`, `request_changed` and
   `charge_exceeds_reservation`. `uncertain_calls` lists what a settlement
   would book, and why one would be refused.
5. **The accounting rule.** A settled call is booked at its full reservation:
   the money reservation (the most the request can cost), the attempt and the
   reserved bytes. That never under-counts spend: whatever the provider
   charged, it cannot have charged more than the reservation. A provider that
   reported a charge above the reservation cannot be booked by the ledger, so
   that call is refused settlement, never booked under its report; it has to
   be reconciled against the provider's own usage record. An unpriced
   selection books the attempt and bytes; its money stays unmetered, as
   before. `provider_turns` lists a turn's settled calls under `settled`,
   with the basis "outcome unknown; full reservation booked by settlement".
   A turn with no settlement, and no early end, has exactly the record it had
   before.
6. **The default output cap stays 2,048 tokens.** It is a spend default; see
   the owner input below. With decision 1, hitting it no longer stops an
   epoch.

**Consequences.**
- A resumed campaign that an incomplete reply, a key rejection or exhausted
  retries had stopped now continues, spending model calls. No journalled
  turn, prompt, plan or digest changes.
- A failed 502 or 503 now books nothing for that attempt; before, it booked
  the full reservation and stopped. A miner whose provider bills such a reply
  would see Carbon under-count it. This is the work list's reading; it is not
  invoice-verified.
- Retries spend `provider_attempts` and wall time. Under a sustained rate
  limit, one call can make up to 7 attempts in one run, and a resume makes
  more. A run with an attempt ceiling (a development grant, a Graphite run)
  reaches it sooner.
- In Graphite's card triage test, a scripted 503 now reaches its unknown
  outcome through the retry (`test_graphite_method_cards`, unchanged and
  passing).
- The loop records new journals: `<turn>-truncated.json` in the epoch
  folder, and `uncertain.json` and `settlement.json` beside each model call.

**Alternatives rejected.**
- *Record an early end `SUCCEEDED`.* A caller that does not accept one would
  then replay it as a success. The row stays as it always was, and the
  `incomplete` record says how the reply ended.
- *Run every call of a reply that ended early.* Its last call may be cut
  mid-arguments; a `run_python` with half a program would spend a trial
  slot on nothing.
- *Settle automatically at the end of a run.* That would resend a possibly
  charged call without anyone deciding to. Settlement stays an explicit
  reconcile action.
- *Book a settled call at its estimate or at zero.* That could under-count
  spend.
- *Treat 500 and 504 as retry-safe.* The request may have been processed;
  they stay uncertain.
- *Retry a key rejection at once.* It fails again until the miner acts.

**Reversal.**
- Drop `accept_incomplete=True` from `run_epoch`; the old refusal returns.
- Remove `unavailable_statuses` from the error semantics: 502 and 503 go back
  to uncertain.
- Set `MAX_AUTOMATIC_RETRIES` to 2.
- Remove the resumable pass in `_rejected`.

Recorded rows stay readable either way: a settled call has a distinct
result, and a reply that ended early is the row it always was.

**Tests (part 2).**

  - 502, 529 and an unreachable provider are retried uncharged, with jitter

  - the ledger ceiling bounds the retries;
  - an unreadable key file is a credential failure;
  - settlement after a timeout, a 500, missing usage and a different model:

**Owner input still open (part 2).** Whether to raise the default output cap
(`model_provider.DEFAULT_SETTINGS.max_output_tokens`, 2,048 tokens) is a spend
default, so it is the owner's. The evidence:
- **Reasoning counts against the cap.** OpenAI's output price includes
  reasoning tokens (`GPT5_MINI_PRICING`), and the default effort is `low`.
- **A stated argument cannot fit.** Under v2 the agent is told it may send
  16,384 bytes of tool arguments. At the roughly 4.2 bytes per token measured
  on a live request on 2026-10-03 (lesson
  `2026-10-03-planner-run-2-output-truncated`), that is about 3,900 tokens,
  so one call at the stated limit cannot fit in a 2,048-token reply.
- **A real reply was cut off.** The Graphite level planner's second live
  reply ran past its 8,192-token output limit (same lesson).
  GRAPHITE-GRANT-PLANNER-02 then sized that role for a medium-effort reply,
  at 32,768 tokens.
- **Cost.** Each extra output token raises the per-call reservation by the
  model's output price: about USD 0.0123 for 8,192 tokens on the pinned
  `gpt-5-mini` (USD 0.0205 to 0.0328), and about USD 0.0006 on
  `deepseek-v4-flash-0731`. Where the provider reports no charge (Engy
  without `x_engy.charged_micro`), the full reservation is what is booked.

A miner can already set `max_output_tokens` per selection (256 to 131,072).

**Unchanged.** Graphite proposes; Carbon's verifier decides (invariants 7.9
and 7.10). A paid call whose outcome is unknown is never resent blind. No live
session was run and nothing was spent. None of this is scientific, security
or production qualification.
