## 2026-10-03 — LP-PROD-G: the battery validator runs as a supervised service behind its intake

**Authority.** OWNER-LAUNCHPAD-PROD-01: the owner, in chat on 2026-10-03,
approved the Launchpad production work list ("approve. you launch this
now"), whose slice G is a real submission endpoint and validation service on
the validator-pinned images. Engineering decisions within that slice,
recorded by the executor. Exposure stays under OWNER-INTAKE-EXPOSURE-01; the
carry-over under OWNER-BATTERY-CARRYOVER-01.

**Decision.**

1. **The service is two processes over one deployment.** The intake
   (`python -m carbon.battery.intake serve`) and the validator daemon
   (`python -m carbon.battery.operate run --every SECONDS`, a new flag: one
   `run` per period; SIGTERM ends it once the pass in flight returns, and a
   pass longer than the supervisor's or unit's 45 s stop grace is killed and
   its run recovered as infrastructure at the next start). Both already
   serialise on the deployment's writer lock, so neither needs the other.
   `scripts/dev/battery_validator_service` adds a service configuration
   (`carbon.battery.validator-service.v1`), `preflight`, `parity`, `status`,
   `backup`, `restore`, `supervise` and `units` (`systemd --user`). A child
   that exits 2 refused its configuration and is never restarted; other
   exits restart with a doubling backoff (1 s to 60 s) and stop after 5
   restarts in 10 minutes. These periods and limits are engineering values.
2. **The preflight fails closed, by named code, and reports every check at
   once.** Owner-only configurations; the pinned worker images present by
   digest and doctor-eligible; the stored binding equal to what a start
   binds from this checkout (`deployment_not_upgraded` names the fields);
   image and contract parity; and, only for a non-loopback bind, the
   recorded exposure, an existing certificate, an owner-only key that loads,
   and the isolated carrier. A `direct` deployment is accepted only with
   `allow_direct_backend` and never beyond loopback.
3. **Parity is identity equality.** Every image the deployment scores with
   needs the manifest miners practise with under the same key
   (`practice_images.image_manifest`, `.torch_image_manifest`), and every
   identity field must match (`parity_image_differs`). The bound contract
   must be this checkout's registered battery contract
   (`parity_contract_differs`). Nothing here picks which image is right.
   *2026-10-03: the direction and codes are superseded by
   OWNER-LAUNCHPAD-PROD-02 (answer 10): the validator's images are the
   standard. See the last section.*
4. **`operate upgrade` binds what a start binds** (`operate.serving_identities`).
   A read-only build runs the in-process backend, and `upgrade` bound that
   backend's identity, so a carrier deployment's next start refused
   `identities_changed` and a second `upgrade` changed nothing. It now binds
   the carrier identity from the pinned manifests; an affected deployment is
   repaired by one `upgrade` (`changed: ["backend"]`). Recorded here because
   it changes the only path that rebinds a deployment.
   *2026-10-03, closed by OWNER-LAUNCHPAD-PROD-02 (answer 9, "yes
   upgrade"): `operate upgrade` on the real v1 deployment is approved. A
   backup of its root, journal and state is taken first, and it runs once,
   at the server bring-up after this work merges.*
5. **An admission refusal that is not a verdict is received again on
   resend** (`intake.RECEIVED_AGAIN`): the window, an undated receipt, a
   missing commitment or commitment reader, an unserved backend. Before,
   only the window was, and the others held a recipe's one submission id
   refused for good.
6. **The Launchpad's intake path consumes an epoch only with a verdict.**
   A submission the worker refused came back as the epoch's feedback with
   state REFUSED. Now every non-verdict is an `OperationRefused` with a
   closed code (`intake_code`), classified `QUEUED`, `UNAVAILABLE` or
   `REFUSED` (`campaign.intake_outcome`) and explained
   (`intake_client.explain`). A refusal named in item 5, or `not_found` for
   the epoch's recorded submission, resends the same candidate once per
   call; a window refusal is resent only once the intake's chain has reached
   the window. A candidate recorded against another intake is refused
   (`intake_changed_since_submission`).
7. **The TLS handshake leaves the accept loop.** The listening socket was
   wrapped with the default `do_handshake_on_connect`, so every handshake
   ran in `accept`, in the single serving thread, with no timeout: one client
   that connected and sent nothing stopped the intake for everyone. Each
   handshake now runs in its connection's thread under the 10 s socket
   timeout. A failed connection is logged by exception type, not by the
   base class's peer address and trace.
8. **Backups are root, journal and state together**, copied under the
   writer lock (SQLite through its backup API), with the intake's inbox and
   transport journal, a manifest of digests and the root's public
   commitment. A restore verifies first and never overwrites (item 12).
   Configurations, TLS material and the `service_key` are not in a backup;
   they move separately, owner-only, when a deployment changes hosts.
9. **Logs are JSON lines of events, counts and exception types**, never a
   peer, hotkey, path, request, case or seed.

**Review repairs** (independent review of this slice, same authority):

10. **Only a configuration exits 2** (`operate.exit_code`). Every
    `EvaluationUnavailable` used to exit 2, so a carrier start refused only
    because Docker was down or still starting (`evaluation_host_unavailable`)
    stopped both children for good and systemd never restarted them. Codes
    naming the configuration or its files exit 2; the host's state, and any
    code not known as a configuration, exit 1 and are restarted within the
    limit. Neither process exits for the host's state any more: the intake
    waits for the deployment before it listens (`waiting_for_host`, backoff
    1 s to 60 s), and `run --every` builds it in its first pass and retries
    each period (`pass_unavailable`). `preflight --wait-for-host SECONDS`
    (the units: 300 s inside `TimeoutStartSec=360`; `supervise`: the same)
    re-checks while the only refusal is `worker.doctor.docker_unavailable`.
11. **Every part is seen by its own lock, however it was started.** The
    intake holds `<inbox>.serve.lock`; `run --every --heartbeat PATH` holds
    `PATH.lock` and keeps an owner-only heartbeat (pid, period, passes, how
    the last pass ended). Under the systemd units no supervisor runs, and
    `status` reported healthy whenever the intake answered. It is now healthy
    only when the intake serves and answers, the daemon is alive with a
    fresh heartbeat (between passes for at most twice its period plus 30 s;
    a pass in flight is never stale) and its last pass succeeded, and every
    supervised child runs. `restore` refuses while any of the three locks is
    held. Locks are probed shared for an instant and every holder retries
    its own briefly, so a probe never makes a start fail.
12. **A restore is all or nothing**, and a failed backup leaves no hidden
    copy of the root. Every destination directory is made owner-only and
    every destination (and SQLite `-wal`, `-shm`, `-journal` beside a
    database) checked free before a byte is written; each member is written
    under a temporary name and linked into place (a link never replaces a
    file); any failure, including the root-commitment check, removes every
    file the restore wrote.
13. **A resend is checked before it is sent.** `not_found` also answers a
    poll signed by another hotkey, so after a signer change the campaign
    resent the frozen candidate under the new hotkey - a second submission
    and admission, using that hotkey's window - and compared ids only
    afterwards. The id the resend would name is now worked out from the
    signer's public hotkey first (`intake_client.submission_id`, which is
    `daemon.submission_identity`), and a mismatch sends nothing
    (`intake_signer_changed`). Every way the trip itself can fail is a
    closed code, so the campaign keeps its candidate instead of ending on an
    exception: `signer_unavailable`, `intake_mismatch`, an HTTP refusal of
    the public facts by its own code, `intake_unreachable` for a non-JSON
    body or a broken connection, `intake_answer_unrecognised` otherwise.
14. **The status probe pins the served leaf**: the certificate the listener
    presents must be the configured file's first certificate, byte for byte
    (`intake_certificate_differs`), not merely one the file's chain trusts.

**Unchanged.** The default bind is loopback; exposing a host, the public
host, DNS name, TLS certificate and firewall stay the owner's
(`docs/development/BATTERY_VALIDATOR_SERVICE_RUNBOOK.md` §5). No scientific
value, threshold, gate or tolerance changed. Carbon holds no hotkey; nothing
writes to a chain or sets weights; scores stay DEVELOPMENT evidence. Tested
on loopback with throwaway deployments only, never the operator's. Not a
security audit, and nothing here is SECURITY_QUALIFIED (AGENTS.md §13).

*2026-10-03, closed by OWNER-LAUNCHPAD-PROD-02 (answer 11, "Approved"): the
owner accepts the security review of the validator service tooling and the

### 2026-10-03 — Closed by OWNER-LAUNCHPAD-PROD-02: miners practise on the validator's images

**Authority.** OWNER-LAUNCHPAD-PROD-02, decision 10 (the owner, answer 10:
"practice on validator images as long as NO ACCESS to hidden test
conditions"). Delegated engineering choices implementing it; no scientific
value, image identity rule or exposure changes.

**Decision.**
1. **The validator's pinned images are the standard.** Parity
   (`service.parity`, `parity --config S`, and the preflight's `parity`
   check) holds each practice manifest to the image the deployment scores
   with, never the other way round. Item 3's comparison is unchanged (every
   identity field, the contract digest); its direction, wording and codes
   now say which side is the standard:
   - `parity_reference_unnamed` is `practice_image_unnamed`, naming the
     validator's image as `standard`;
   - `parity_manifest_unreadable` is `practice_manifest_unreadable`;
   - `parity_image_differs` is `practice_image_differs`, naming the fields,
     the validator's image as `standard` and the practice one as `practice`
     (they were `validator` and `miners`);
   - the next step publishes the validator's image for practice; it no
     longer offers to change the validator's image to match practice.

   `parity_contract_differs` keeps its code: its standard was already this
   checkout's registered contract, reached by `operate upgrade`.
2. **What practice reaches is the images' public build identity**
   (`service.practice_standard`: `IDENTITY_FIELDS` per image, read from the
   manifests alone). Every parity report names it (`practice_standard` is
   `validator_pinned_images`) and what is withheld from practice
   (`PRACTICE_WITHHELD`: private cases, seeds, the private root, references
   and per-case results). The image is code; practice scores against the
   public PRACTICE cases only, and nothing in this tooling reads a hidden
   test condition into what it prints.
3. The runbook (`BATTERY_VALIDATOR_SERVICE_RUNBOOK.md` §3) says the same and
   lists the new codes.

**Tests** (`tests/cpu/test_battery_validator_service.py`):
`test_parity_holds_practice_to_the_validators_images` (the renamed codes,
the `standard` and `practice` fields, the next step, an unreadable practice
manifest, and the report's standard), and
`test_practice_on_the_validators_images_reaches_no_hidden_test_condition`:
with a started carrier deployment, the practice standard is exactly the
validator image's identity fields, and neither it nor the parity and
preflight reports carry the private root, a screening case id, its inputs or
duplicates, the batch fingerprint, a reconstruction seed drawn from that
root, or any private path of the deployment.
