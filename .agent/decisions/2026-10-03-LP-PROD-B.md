## 2026-10-03 — LP-PROD-B: the MCP door's errors are correct, its tools discoverable, its schemas natural

**Authority.** Delegated engineering decisions (executor, slice B), within
OWNER-LAUNCHPAD-PROD-01: the owner asked on 2026-10-03 for the miner front end
to be zero-friction, production-level and state of the art, and approved this
work list in chat ("approve. you launch this now"). Nothing here changes a
scientific value, threshold, gate or tolerance, live economics, a default
spend, a chain write or weight, the public exposure of any host, or any
authority boundary. The signer still holds every key; registration stays the
miner's to sign; miner compute stays link-only; no exam or hidden material
reaches a miner; one owner-lock holder per campaign. Frozen campaign records,
prompts and tool lists are untouched: the agent loop's `research_tools.TOOLS`
and its descriptions are not edited, only how the MCP door describes them.

**Decisions.**

1. *A registered correction reaches the client.* The SDK now returns
   `correction_code`, `field` and `task_correction(code, field, value)`. The
   adapter accepts that shape and the older one, and still never forwards
   arbitrary text: the code must be registered, the field must be one the SDK
   may name (`NULLABLE_TASK_FIELDS` or a registered `arguments_json.<name>`),
   and the text must equal one of the two texts `task_correction` can make for
   that code and field. Field and text are then put in this wire's object terms
   (`arguments.name`, not `arguments_json.name`); `json_string_required`, whose
   registered text describes the JSON-string wire, gets an object-wire text.

2. *Pre-dispatch stops are told apart by where they were raised.* A failure is
   reported with `dispatch_may_have_occurred=false` only where that is a fact:
   raised inside the operation-id binding `ResearchMinerTools.call` makes before
   `_call`, or inside the admission check `_call` makes before it signs (read
   from the exception's own traceback, matched by code object). The message
   then picks the code: `CAMPAIGN_ELAPSED_BUDGET_REACHED`,
   `CAMPAIGN_ADMISSION_STOPPED`, `OPERATION_ID_REUSED`; any other failure at
   those sites is an `OPERATIONAL_STOP` that started nothing. The same text
   raised anywhere else keeps the conservative answer. On a controlled
   campaign (every product and grant campaign) the binding's `ledger.reserve`
   runs campaign control's checkpoint first, so a spent time limit is refused
   there as `DispatchStopped("original campaign deadline reached")`: that maps
   to `CAMPAIGN_ELAPSED_BUDGET_REACHED`, any other control fence to
   `CAMPAIGN_ADMISSION_STOPPED`, so a numerical start and a read on the same
   spent campaign report one code (review fix; pinned through the real
   `_AdmittedConnection` and a real product ledger). The elapsed code's text
   names every time limit it covers: the miner's elapsed budget, a grant's
   expiry, or a host clock that moved backwards. The admission-stopped text
   tells an attached session to detach, resume or reconcile, and attach again.
   Typed exceptions raised at those sites would be cleaner; they belong to
   slices C and D (handed off), and the site rule stays correct after they
   land.

3. *Tasks refusals read like the plain tools'.* One `serving.refusal` line -
   `CODE; dispatch_may_have_occurred=...; [field=...;] next_action=...` - for
   both. An invalid argument names the field only when the schema declares it,
   never a key the caller invented. `tasks/get` and `tasks/cancel` answer
   `-32602 TASK_NOT_FOUND; retry=false` only for a task this campaign does
   not hold (unknown or another miner's - the provider cannot tell them apart
   either, so one answer and no oracle) or an invalid id. Every other failure
   is `-32603 <CODE>; retry=true|false` under its own code and never claims
   the task is missing (review fix: `INVALID_RESULT` and `OWNER_BINDING` were
   folded into TASK_NOT_FOUND, whose "Nothing changed" was false after a
   cancel and could send an agent to start its running work again).
   `retry=true` only for the codes after which the same observation may
   succeed (`serving.OBSERVATION_RETRYABLE`: an operational stop, a campaign
   not admitting, a signer not running, refusing or slow); everything else,
   including any code added later, is `retry=false`. A projection failure is
   `INVALID_RESULT`, whose observation text says a cancellation may already
   be accepted and not to start the task again. The provider's bound on
   observing one task (`BOUND_EXCEEDED`) becomes its own permanent
   `OBSERVATION_LIMIT_REACHED`. Observation texts never ask for an
   operation_id. The adapter reports the task provider's typed
   `TASK_NOT_FOUND` as its own code.

4. *Growing the surface is announced.* The open-tier server advertises
   `listChanged` for tools, resources and prompts on its stdio handshake, and
   every call that adds or removes tools announces it (`open_tier.announce`):
   on the session for a handshake-era client, on the subscription bus for a
   2026-07-28 one. Best effort, never failing the call; results still name the
   tools added. A session that reconnects after setup's review gets the
   registered tier's operations at once, and setup status says whether
   `carbon_launch` is in this session. When it is not because the written
   profile failed to load here, status says so and sends the miner back to
   `carbon_setup_review` (a reconnect with that profile would fail the same
   way), and a review whose profile does not load still returns its result
   rather than a bare error; otherwise status gives the reconnect command,
   with `--state-dir` when setup's records are not in the default directory.
   It no longer names the nonexistent `carbon_operations`.

5. *Research tools are described and shaped for an agent.* Each tool carries
   the SDK's own per-operation description in object terms, so
   start_research_task lists every workspace action and its fields. strategy,
   action and arguments default to null. The description says run_python and
   run_julia repeat hypothesis and expected_effect inside arguments, and
   poll_sequence is documented (0, then +1 per poll, at most 9999, shared).

6. *IDs are optional and stated.* `operation_id` defaults to a server-generated
   `mcp-auto-<32 hex>` returned in the result; on a start, passing one makes a
   retry idempotent. Its schema states pattern, minLength 16 and maxLength
   114, and each tool's description says what the id does there and nowhere
   else: a start's idempotency key (with `OPERATION_ID_REUSED` only for the
   numerical starts the ledger binds), a cancel's cancellation identity, and
   "only recorded" on every other tool (review fix: one shared text claimed
   replay semantics for all). `cancel_research_task` generates no random id:
   omitted, it uses `mcp-cancel-<task_id>`, the identity `tasks/cancel` uses
   and the task provider falls back to, so a retried cancel after a lost
   response is accepted again instead of refused as a second cancellation of
   a task whose first is pending (review fix; pinned through the real
   provider). The 16-character minimum stays: it keeps clients from reusing
   short ids across sessions, which would replay an old result. Launch's `idempotency_key` is
   optional on the MCP door, generated as `mcp-<32 hex>` and returned; the
   description says a retry without it launches a second campaign. The two
   character sets are stated rather than aligned: `idempotency_key` takes no
   `.` or `:` because the runner's key check (slice C) does not.

7. *Operation schemas state what the bodies require.* `BODY_REQUIRED` marks
   launch's `challenge` and `challenge_version` required in the MCP schemas
   while the closed-request gate leaves them optional. An MCP call that omits
   one is therefore refused by the SDK's schema validation before the body
   runs; the browser door is unchanged and still gets the body's specific
   refusal (`challenge_required`). `CHOICES` gives agent, halt's action and
   note_kind as enums (the latter two pinned by test to the values
   `campaign_view` and the runner check). Setup's agent names are accepted
   (`carbon-autonomous` = `autonomous`, `own-agent` = `none`), normalised
   before every gate so a replay under either name is one request; `hermes` is
   not aliased (on MCP the enum refuses it at validation, on the browser
   `invalid_agent`). Refusals after validation are JSON `{error, field,
   next_step}` from one table, following the SDK's `Error executing tool
   <name>: ` prefix; every description says so, and that a schema violation
   reads as the SDK's own validation message. Setup's compute schema says
   `challenge` and `gpu_image_manifest` go only with a GPU choice.

8. *Results.* run_output's images travel as MCP image content, the JSON naming
   each by content index instead of carrying base64; its description now says
   stderr is kept. A research result over 1 MiB is cut to fit, largest strings
   and lists first, never below 1024 characters or 16 elements, with a
   `truncation` record naming each cut (the first 16, and `cut_total`); only a
   value over 16 MiB, or one that cannot be cut to fit, is still
   INVALID_RESULT. The record has 8 KiB of room - its paths are printable
   ASCII of at most 160 characters - and the payload is re-measured with it,
   so a cut result never leaves over the limit. Each pass cuts every disjoint
   node it needs, at most 8 passes, stopping at a pass that cuts nothing
   (review fix: 4 KiB could be too little, and 64 single-cut passes re-encoded
   a large value on the event loop).

10. *The door's own README says what the door does.* `carbon/miner_mcp/
    README.md` describes the list-change announcements, the refusal forms and
    codes, the optional ids, the tasks/get error split and result truncation,
    and no longer speaks of a grant in the client workflow.

9. *Attach mode and parallel calls.* While this session is attached to a
   campaign, practice, freeze_candidate, submit, resume and halt
   action=reconcile on it answer `campaign_busy` with next step
   `carbon_detach_campaign` before their body starts a run that could not take
   the lock. observe, campaign_view, messages, note and run_output take no
   owner lock and keep working. The catalogue lists only the extensions the
   live server offers, so Tasks is absent on the attach path. The skill text no
   longer speaks of a grant. One attach or detach runs at a time
   (`attachment_busy`), a detach the client asks for is refused while research
   calls are in flight (`research_calls_in_flight`), a parallel review attaches
   the operations once, and shutdown always releases.

Tests: `tests/cpu/test_lp_prod_mcp_door.py`; the retried-cancel case in
`tests/service/test_mcp_task_supervisor.py`; the updated replay-conflict
assertions in `tests/cpu/test_standard_mcp_adapter.py` and
`tests/service/test_standard_mcp_stdio.py`.

## 2026-10-03 — W1 (integration wiring): the door verifies corrections with the builder's rule, and reads one catalog of next steps

**Authority.** Delegated engineering decisions (integration fixer W1), within
OWNER-LAUNCHPAD-PROD-01, closing two handoffs integration testing found
unwired. Nothing here changes a scientific value, live economics, a default
spend, a chain write or weight, a host's exposure or an authority boundary.

1. *Every correction the SDK makes crosses the door (B<-D).* Decision 1 above
   rebuilt only `task_correction(code, field, None|"null")`, and only for
   `start_research_task`. Slice D's corrections also name the tool and list
   Carbon-written choices, and refuse other operations by name, so they
   reached MCP clients and the Control Center's tools page as INVALID_RESULT
   that "may have dispatched". `_correction` now verifies a record with
   `research_tools.correction_parts`, the builder's own rule (see LP-PROD-D,
   W1): a registered code, a registered field, a registered tool, and listed
   values drawn from the code's closed public list. It forwards only text that
   rule rebuilds exactly, for any research operation; a correction naming
   another tool than the one called is refused. The older field-less shape
   (the registered text alone) still crosses. `json_object_required` gains
   object-wire wording, as `json_string_required` has.
2. *One next step per code at both doors (B<->C).* The MCP door's
   `operations.refusal` read B's own steps (`REFUSALS`, `GENERIC_STEP`) while
   the browser's door read C's `supervisor.NEXT_ACTIONS`: 46 of C's 58 codes,
   `evaluation_unavailable` among them, got a generic step over MCP, and most
   of B's codes got no step in the browser. `REFUSALS` becomes
   `REFUSAL_FIELDS` (code to the field to correct, nothing else); the steps
   moved into `NEXT_ACTIONS`, which both doors, `last_refusal` and the
   refusal catalog read. The attach and detach refusals read it too. The one
   door-specific text kept is `campaign_busy` while this very session is
   attached ("call carbon_detach_campaign"), which only this door can know.
