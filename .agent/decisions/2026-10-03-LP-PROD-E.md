## 2026-10-03 — LP-PROD-E: the miner's install, update and setup describe one install

**Authority.** OWNER-LAUNCHPAD-PROD-01. On 2026-10-03 the owner asked for a
zero-friction, production-level and state-of-the-art miner front end,
"our entire workforce facing application". The owner approved the Launchpad
production work list in chat: "approve. you launch this now". This record
holds the engineering decisions of slice E, the install and update path. They
are delegated to the executor. No scientific value, threshold, gate or
tolerance, live economics, chain write, public exposure or security
acceptance is decided here.

**Why it is needed.** Observed live 2026-10-03: after a reinstall at a new
ref, setup still showed compute as checked, recorded at the old revision and
images, and Review wrote a runner profile with the old accepted revision. The
same audit (main at `dff575f`) found more friction:
- the installer kept a dirty checkout (it counted untracked files), and the
  image build then failed on any untracked file;
- a `--ref` outside main was refused only later, by setup
  (`clean_accepted_checkout_required`);
- disk space was never checked;
- the environment lacked the `archive` group that documented `uv run`
  commands name;
- the restart command was printed only with `--no-start`;
- the miner learnt at submit that no evaluation endpoint existed;
- registration came with no command to run;
- the miner docs had drifted from the installer.

**Decisions.**

1. **A compute check pins what it checked.** `EnvironmentSetup.compute`
   records each image manifest's sha256 (`manifests`). A check is *stale*
   when any of these holds:
   - a pinned manifest was rebuilt or removed;
   - the check predates pinning;
   - once the installer has recorded an install (`environment/installation.json`),
     the check was made at another revision than the installed one, or than
     this checkout's HEAD, or with other image paths than the installer
     recorded.

   Setup shows a stale check as unchecked, with its reasons and the step that
   clears them (`next_step`). `profile()`, and so Review, refuses it with
   `compute_check_is_stale` and next step "<step>: <reasons>". The step is
   "check Compute again in setup" when a new check clears every reason: while
   this checkout is still the revision the installer installed, a new check
   is made at HEAD with the images setup fills in from the installer's record.
   It is "run scripts/install_miner.sh --update" when the checkout moved since
   the install (a `git pull`, or an update whose build failed after the
   checkout moved) or the install record is unreadable: a new check would be
   stale again for the same reason, and only the installer records a new
   install. A developer checkout with no install record is held to the
   manifest pins only. A check recorded before this change is stale once, by
   design: it predates pinning.
2. **After every install, setup is checked against it.** `install_miner.sh`
   step 5 runs `python -m scripts.dev.miner_launchpad.environment_setup
   after-install`, which:
   - writes the install record: the checkout's revision, and each recorded
     manifest's digest and image ID;
   - sets a stale compute check aside (`compute_set_aside`, with its reasons)
     and the profile with it: it drops the profile marker and moves
     `runner-profile.json` to `runner-profile.stale.json` in the same
     owner-only directory, because the controller attaches
     `runner-profile.json` on start whenever it exists. The miner's own
     intakes from that profile are kept in `profile_set_aside`; setup's
     evaluation state shows each as `set_aside_intake` and says to name it
     again at Review, which writes only the intakes it is given. The next
     written profile clears the marker;
   - checks this machine's CPU or GPU compute again with the new images, as
     setup's own check does: no network and no cost;
   - writes a profile written before again, through Review. It keeps the
     intakes the miner named (`source: yours`) and looks up Carbon's
     published ones afresh.

   The miner's own remote setup is never reached: it needs the new GPU
   worker, so the report tells the miner to check Compute again and send or
   push it. Each refusal is reported with its next step and is not retried.
   The installer prints what changed: the revision, each image, compute and
   the profile.
3. **`--update`.** It moves the checkout to the latest main, or to `--ref`,
   which must be in main.
   - When that revision's installer differs from the one running, the new
     installer carries on with the same arguments. Step 2 is skipped then
     (`CARBON_INSTALL_AT` names the revision it moved to), so steps added
     later run on the first update that brings them.
   - It rebuilds every image, and the GPU worker when one was built before
     (recorded, or at the accelerator script's default path). The GPU worker
     build needs no local GPU. A plain install does the same: it also moves
     the checkout to the latest main, and an old GPU worker would otherwise
     be checked again beside images of the new revision.
   - It starts no second Control Center. It restarts the user service when
     one is installed; otherwise it prints the start command.
   - It refuses, before the checkout moves, a target revision whose
     installer has no `--update` (an `--update --ref` to a revision from
     before this change), and says to run it without `--update`. An install
     made before this change runs the installer once with `--no-start` (the
     old installer moves the checkout to the latest main), then `--update`.
4. **Nothing changes under a running Control Center.** The Control Center
   holds `owner.lock` in its state directory while it runs. Before anything
   moves, the installer tests that lock with `flock -n`. If it is held, the
   installer stops and names how to stop the Control Center. A campaign
   running in a moved checkout would fail at its next revision check.
5. **Step 2 fails fast.**
   - A checkout with any change, untracked files included (the same rule as
     `c03_worker_image.sh`), stops the install before any fetch. The message
     lists the first ten paths and how many more, and gives the exact
     command:
     `git -C <checkout> stash push --include-untracked -m 'set aside by install_miner.sh'`,
     with `stash pop` to bring them back. The listing is read from a
     here-string, not a pipe: with thousands of paths a pipe into `head`
     ended the installer by SIGPIPE before it printed the command.
   - `--ref` is fetched and must be an ancestor of the freshly fetched
     `origin/main`, the rule `accepted_implementation` applies later.
6. **Stated disk requirement.** Before anything changes, the installer needs
   5 GiB free beside the checkout and 12 GiB where Docker keeps its images,
   24 GiB with the GPU worker. These are about twice what was measured on
   2026-10-03: the environment 0.75 GiB plus uv's cache, the worker image
   0.97 GiB, the analysis image up to 4.4 GiB and the GPU worker 6.04 GiB.
   When the checkout and Docker's root are on one filesystem (WSL's
   default), it needs the sum there. When Docker's root is not a local
   directory, or df cannot read the free space, the installer states the
   figure instead of guessing.
7. **One environment for every documented command.** The installer syncs
   `science-jax chain archive mcp`, so a documented `uv run --group ...`
   never re-syncs it. The signer doc no longer tells a miner to run a
   `uv sync` with fewer groups, which removes the rest.
8. **One terminal.** The new console script `carbon-control-center` runs
   `scripts/dev/miner_launchpad/controller.py` from the checkout.
   - Its entry point is a new top-level package, `carbon_control_center`, a
     launcher only. The `scripts` package is not installed, and the existing
     `carbon*` package discovery includes the launcher with no change to
     `[tool.setuptools]`.
   - `install_miner.sh --service` writes, enables and starts the systemd user
     unit `carbon-control-center`. Later installs and updates find the unit
     and rewrite and restart it.
   - The unit's output, which carries the session token, is appended to
     `control-center.log` in the owner-only state directory under
     `UMask=0077`, never to the journal. The installer creates the log
     owner-only (mode 0600) before it starts the unit, since systemd leaves
     an existing file's mode alone, and refuses a log that is a symbolic
     link.
   - The output is line-buffered: the unit sets `PYTHONUNBUFFERED=1`, and the
     launcher sets line buffering on its own streams. Python block-buffers
     output to a file, so without this the token line reached the log only
     when the Control Center exited (review finding, 2026-10-03).
   - Unit paths must be plain absolute paths (no space, quote, `%` or `$`),
     so systemd expands and splits nothing.
   - The service is opt-in. A user service does not inherit the shell's SSH
     agent or `~/.local/bin`, so a remote setup that needs the agent, or
     Hermes, works from a terminal-started Control Center. The docs say so.
     Lingering after logout stays the miner's own system setting.
   - Every install prints the command that starts the Control Center again.
9. **Carbon's evaluation endpoints are published data.**
   `scripts/dev/miner_launchpad/published_endpoints.json` lists entries of
   `network`, `netuid`, `challenge`, `intake_url` (https) and
   `receiver_hotkey` (ss58). It starts empty, and an operator adds the live
   entry by pull request.
   - The list is closed and read fail-closed: a malformed list publishes
     nothing and says so. Entries for another network are skipped, and there
     is one entry per network, subnet and Challenge.
   - Review writes the published entry into the profile's `intakes` for each
     Challenge the miner did not name. It reaches no network for it: the
     entry was reviewed into the repository, and the intake client checks the
     intake's chain and Challenge at submit.
   - `receiver_hotkey` is informational. Review does not write or check it,
     and the intake client signs for the receiver the intake reports, without
     comparing it with the published one. Setup shows it with a note saying
     so. Checking it at submit is a handoff to the intake client's owner.
   - A Challenge with no endpoint gets a `no_evaluation_endpoint` warning.
     The profile is still written, never silently. Setup's new `evaluation`
     state shows each Challenge's intake and whose it is, or says plainly that
     none is published, or that one has been published since Review.
   - The prelaunch review gains `evaluation_endpoints`. Its readiness
     `independent_development_evaluation_available` becomes
     `CONFIGURED_FOR_ALL`, `CONFIGURED_FOR_SOME`, `NOT_CONFIGURED` or
     `NO_CHALLENGE_SUBMITS_THROUGH_AN_INTAKE`, in place of
     `RESOLVED_AT_FINAL_PHASE`. It reads configuration only. Only a published
     endpoint's URL is shown; a miner's own intake and validator path stay
     private.
   - The prelaunch review is display only. The launch pin digests the
     profile, not this projection, so no frozen campaign changes.
10. **Registration has a command.** `chain_onboarding.prepare` also returns
    `command`, a template:
    `btcli subnet register --netuid 567 --network test --wallet.name <your wallet name> --wallet.hotkey <your hotkey name>`.
    The subnet is the context's. The network is btcli's name for the context's
    network (`test` for `testnet`) when the context's endpoint is the one the
    operator config pins (`DEFAULT_ENDPOINT`), and the endpoint itself
    otherwise, so the command cannot drift from the context `prepare`
    validated. It is marked UNVERIFIED (Carbon has not run btcli). Carbon still
    signs nothing, runs nothing and reads no cost.

**Owner-reserved, proposed and not changed: the worker image's source
digest.** `c03_worker_image.sh` sets `SOURCE_TREE_DIGEST` to the sha256 of
`git archive HEAD`, the whole tree. `accepted_implementation` computes the same
digest, and `verify_current_worker` requires the two to be equal. So any
commit, even a documentation-only one, invalidates every installed image, and
every update rebuilds all images. That digest is part of the pinned evaluation
identity, so this slice leaves it unchanged.

*Proposal:* a new versioned identity (`carbon.c03.worker-image.v2`, with a
recorded `source_scope`) that digests only what the build copies into the
image: `git archive HEAD -- pyproject.toml uv.lock README.md carbon`
(`.devcontainer/Dockerfile.reconstruction-worker` lines 21 and 22; the recipe
is already pinned by `BUILD_RECIPE_DIGEST`). v1 manifests, campaigns and
epoch plans would keep replaying under v1.

*Effect:* a docs-only or `scripts/`-only commit would no longer require
rebuilding images. The accepted revision would still move, so the compute
check runs again, and passes without a rebuild.

*Owner decision needed:* whether the worker's source identity may be narrowed
to its build inputs, as a new versioned rule.

**Unchanged.**
- Carbon holds and reads no key. The miner's signer signs and the miner signs
  registration.
- Miner compute is link-only: an update never reaches a remote setup.
- No exam or hidden material reaches a miner.
- No scientific value, image identity rule, live economics or chain write
  changes. DEVELOPMENT evidence only.
- Nothing here is security-qualified. The installer, the service unit and the
  published-endpoint path need the dedicated review AGENTS.md §13 requires.

Tests: `tests/cpu/test_miner_install.py` (sandbox checkout with a local origin
and stand-ins), `tests/cpu/test_miner_setup_after_install.py`, and additions
to `tests/cpu/test_miner_launchpad_prelaunch.py` and
`tests/cpu/test_chain_onboarding.py`.

### 2026-10-03 — LP-PROD-W2: a stale runner profile is never attached

**Why.** Integration testing found that the Control Center attached
`runner-profile.json` on every start, and `carbon-mcp --configuration`
attached any profile, whatever the installer had installed since. Only
`after_install` moved a stale profile aside, so a profile left behind was
attached and failed later inside a campaign. That happens when the
after-install step did not run or refused, after a `git pull`, when images
were rebuilt by hand, or when compute was checked again without a Review.

**Decision.** Delegated engineering, within OWNER-LAUNCHPAD-PROD-01.
- `EnvironmentSetup.profile_staleness(cfg)` applies decision 1's comparison
  to a runner profile. The comparison is now `_install_drift`, shared with
  the compute check, whose reasons and steps are unchanged. It compares the
  profile's accepted revision and image manifest paths with the installer's
  record and this checkout, and checks each pinned image's manifest: gone,
  or naming another image ID than `runtime.images`. The step is
  `run scripts/install_miner.sh --update` when the checkout moved or the
  record is unusable; otherwise it is
  `check Compute again in setup, then review to write your profile again`.
- Only a profile in setup's own directory, beside `installation.json`, is
  judged. An operator's own profile elsewhere, and a checkout the installer
  never ran in, are not; C's `checkout_refusal` still guards each launch.
- `RunnerAdapter.for_profile` refuses such a profile with C's code
  `carbon_updated_rerun_installer` and `next_step` "<step>: <reasons>". So
  every door that constructs a host refuses it:
  - the Control Center, on start and when setup's page attaches a written
    profile. It starts without the profile and prints the code and next
    step, and `GET /api/v1/research` answers C's `CARBON_UPDATED` preflight
    with `next_step`;
  - `carbon-mcp --configuration`, which prints the code and C's next action;
  - a detached supervisor, which exits.

**Unchanged.** `after_install`, the compute check, the image identity rules
and C's `checkout_refusal`. Nothing scientific or economic.

**Handoff.** `standard_cli.unavailable_message` prints C's fixed next
action; it could add the refusal's own `next_step` (C, B).

**Tests.** `tests/cpu/test_lp_prod_wire_runtime.py`.
