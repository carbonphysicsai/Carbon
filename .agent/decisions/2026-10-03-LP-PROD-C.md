## 2026-10-03 — LP-PROD-C: one campaign supervisor, and campaign state that tells the truth

**Authority.** Delegated engineering decisions (executor), within
OWNER-LAUNCHPAD-PROD-01: the owner's instruction of 2026-10-03 to make the
miner front end zero-friction and production-level, and the owner's approval
of the Launchpad production work list in session ("approve. you launch this
now"). Slice C of that list: the campaign supervisor and truthful state.
Nothing here changes a scientific value, threshold, gate or tolerance, live
economics or a default spend value, any chain write or weight, what a host
exposes, or any key-holding boundary. DEVELOPMENT evidence only.

**Why.** Observed live on 2026-10-03 and confirmed in the code at `4be2642`:
1. A launch, practice, freeze or submit ran on a daemon thread of whichever
   process received it, including a short-lived MCP stdio process. When that
   client exited the thread died: the campaign stayed QUEUED with no
   `campaign-manifest.json`, and attaching to it failed ("private bounded
   operator record required").
2. `RunnerAdapter.close` sent an irreversible stop to every live thread, so
   closing an agent mid-practice stopped its campaign for good.
3. Every start of the Control Center or of `carbon-mcp --configuration`
   settled every campaign not COMPLETED, STOPPED or PAUSED with cleanup
   assumed failed, which flagged idle READY campaigns RECONCILIATION_REQUIRED.
   Resuming a launch never prepared started a run with no product, which is
   the retired grant path.
4. Pause or Stop on a campaign nothing was running stayed PAUSE_REQUESTED or
   STOPPING for ever, and Resume was disabled for PAUSE_REQUESTED.

### D1. Who runs campaign threads

`scripts/dev/miner_launchpad/supervisor.py` defines four roles for the one
campaign host (`RunnerAdapter`):
- **SUPERVISOR**: the Control Center, while it runs. It runs its own
  requests' threads and drains what clients queue.
- **DETACHED**: when no Control Center is running, a client that queues work
  and finds no supervisor alive starts
  `python -m scripts.dev.miner_launchpad.supervisor --configuration PROFILE`
  with `start_new_session` (detached process flags on Windows), its standard
  streams on the null device so it never writes to an MCP client's stdio. It
  exits once nothing is queued and none of its threads is alive for 10 s. It
  stays while a paused autonomous campaign's thread waits at its checkpoint,
  because that thread is still the campaign's (see handoff to slice A).
- **CLIENT**: every MCP door (`for_profile`'s default). It runs the
  operations table's gates, queues what was admitted, wakes or starts the
  supervisor, and observes. It never owns a campaign thread.
- **INLINE**: the historical single-process behaviour, for fixtures and tests
  that drive a host directly. No production door constructs it.

Exactly one supervisor holds the lock for a runner database and principal: an
OS lock (`controller.owner_lock`) in `.supervisor-<digest>` beside the
database, released by the OS when its process exits. Only the holder starts
queued work or recovers campaigns. Every campaign's own ownership lock is
unchanged: one holder per campaign.

### D2. The dispatch queue

`launchpad_dispatch`, in the runner's own database (owner-only): what a client
admitted, as QUEUED → RUNNING (claimed by one supervisor) → DONE. A claimed
item is never started twice. A RUNNING item whose supervisor died is marked
`interrupted` and never replayed: the campaign's ledger, not the queue, says
what may have been dispatched, so no paid model call with an unknown outcome
is resent. The supervisor reads the runner profile again and refuses an item
admitted under a different profile (`profile_differs_from_request`); it never
runs one profile's request under another.

### D3. A launch carried out where it was not received

A launch now records its admitted request (`launchpad_campaigns.launch_request`,
without the idempotency key). A run that must create the campaign and holds no
in-memory admission (a supervisor in another process, or a restart before the
campaign was prepared) rebuilds the `ProductLaunch` from that record:
- the record must reproduce the recorded identity and request digest
  (`launch_record_differs`) under the same profile
  (`profile_differs_from_request`);
- its Challenge, model choice and budget are validated again exactly as at
  launch;
- registration is read again, with the signer probe, because a
  `RegisteredMiner` can only be built by a read and the one that admitted the
  launch lived in the receiving process. The frozen manifest therefore
  records the observation the campaign actually started under; downstream
  only its hotkey is compared, and it cannot differ.
- A row recorded before this decision has no record and is refused by name
  (`launch_choices_unrecorded`: stop it and launch again). Nothing ever runs
  with no product again.

### D4. Closing pauses or detaches, never stops

Closing a client changes no campaign (its attachment, if any, is detached as
before). Closing a supervisor asks each campaign with a live thread to pause,
records `paused_when_supervisor_closed`, waits up to 5 s for them to settle,
and releases the supervisor lock. One that does not settle in time is settled
from its ledger by the next supervisor's recovery (PAUSED, or
RECONCILIATION_REQUIRED if work may be outstanding). Closing the Control
Center does not hand running campaigns to a detached supervisor: that would
keep model and compute spend running after the miner closed their surface.
Pause is the conservative, one-call-reversible choice; see Owner decisions.
Work still QUEUED when a supervisor closes waits for the next supervisor; a
client that observes it with none alive starts one (at most one per 3 s).

### D5. Recovery

Run by the supervisor when it takes the lock (INLINE: at construction, never
re-dispatching). For each campaign whose ownership lock is free:
- settled campaigns (READY, PAUSED, INTERRUPTED, COMPLETED, STOPPED,
  RECONCILIATION_REQUIRED) are left exactly as they are;
- a campaign whose ledger still says a process was working (QUEUED,
  RECONCILING, RUNNING, PAUSE_REQUESTED, RESUME_REQUESTED, STOPPING) is
  settled with the real cleanup check (`RunnerAdapter._cleanup`):
  RECONCILIATION_REQUIRED only when work may be outstanding or cleanup is not
  verified, otherwise READY (the miner selects and nothing was asked),
  INTERRUPTED, PAUSED or STOPPED as asked;
- one with queued work and nothing outstanding is left to that work, so it is
  not reported interrupted first;
- a launch admitted and never prepared (row QUEUED, no frozen manifest, no
  recorded refusal, its choices recorded, nothing queued, not paused or
  stopped) is queued again, once per lock acquisition, and carried out with
  its recorded choices (D3). One that was refused waits for the miner's
  explicit Resume.

The work list's "skip campaigns with no RESERVED/HELD operations" is read as:
settled campaigns are skipped, and a campaign left mid-flight with nothing
outstanding is settled by the real check rather than left reading RUNNING with
nothing running.

### D6. Idle controls settle at once

Pause, Stop and Reconcile take the campaign's ownership lock without waiting:
if it is free nothing will ever act on the request, so it is settled now with
the real cleanup check (PAUSED, STOPPED, or for Reconcile READY or
INTERRUPTED; RECONCILIATION_REQUIRED while work may be outstanding). If a live
holder has it, Pause and Stop stay requested for that holder's next
checkpoint, and Reconcile is refused `campaign_busy`. Resume is offered for
PAUSE_REQUESTED (it cancels a pause not yet settled) and for a stranded QUEUED
launch.

To keep that true:
- practice, freeze and submit are refused at once on a campaign not yet
  prepared, complete, stopped, paused or awaiting reconciliation, by name;
- an operation, like a run already did, never starts over RESERVED or HELD
  work (`unresolved_operation`, to reconciliation);
- a run or operation that ends while a pause or stop was asked settles
  PAUSED or STOPPED, not READY (`CampaignControl.settled` ranks READY above a
  pending pause);
- an operation refused before dispatch, including a credential refusal,
  settles the generation it took instead of leaving it RECONCILING;
- detaching an agent-less campaign settles it READY, not INTERRUPTED
  (`standard_cli._waits_for_its_miner`).

### D7. The published contract: `last_refusal`, `in_flight`, `recovery`

The observe document (`RunnerAdapter.get`: the `observe` operation, the
browser's `/api/v1/research/<id>` and every list row) and the campaign view
(`carbon.control-center.campaign-view.v1`, additive) gain:
- `last_refusal`: `{code, next_action, at, operation, kind}` or null. `code`
  is a closed identifier (`[a-z][a-z0-9_]{0,63}` or upper case); any other
  is recorded as `operation_refused`, never echoed. `next_action` comes from
  `supervisor.NEXT_ACTIONS`; a code it does not list (a new validator intake
  code, say) is shown with `FALLBACK_ACTION`, so it reaches the miner before
  the table names it. `at` is Unix seconds. `operation` is `run`,
  `practice`, `freeze_candidate`, `submit` or null. `kind` is `refused`
  (nothing dispatched), `interrupted` or `paused`. It is set only where no
  caller was waiting (on a supervisor thread, or by recovery), and cleared
  when the next attempt is admitted. A refusal returned to the caller stays
  the caller's error and is not recorded.
- `in_flight`: `{operation, state (QUEUED or RUNNING), since,
  supervisor_running}` or null.
- `recovery`: `[{action, operation}]`: `resume`/`resume`, `stop`/`halt`,
  `reconcile`/`halt`; empty when nothing is needed.

Carbon's agent selecting a candidate the validator did not evaluate is
reported the same way: `run_agent` and `execute` now return that refusal's
code (`research_campaign`), and the run records it with operation `submit`.
The decision note the agent path writes, and every frozen rule, prompt and
digest, are unchanged.

**Tests.** `tests/cpu/test_launchpad_supervisor.py` (new) covers each
decision. Deliberately changed assertions: an idle Stop now reads STOPPED
(`test_stop_and_retained_readback_need_no_chain_read`,
`test_a_retired_grant_campaign_stays_readable_and_stoppable`), and an
agent-less campaign is READY after its client detaches
(`test_actual_gateway_public_workflow_and_restart_over_stdio`).

## Part 2: named refusals, truthful submission, attach and resume

**Why.** Observed live on 2026-10-03 and confirmed in the code: a submit
refused on its thread (no validator for the Challenge) answered SUBMITTING
and the page said "Submitted"; the HTTP door answered every ValueError and
RuntimeError `research_reconciliation_required`; `carbon-mcp` printed one
sentence asking the miner to verify six things; a stale accepted revision
surfaced only as an interrupted campaign; any change to the profile refused
every resume; a paused campaign could not be attached, so the Tools tab never
opened on an autonomous campaign; practice on a held campaign answered
PRACTICING and then failed; one unreadable campaign failed the whole campaign
list ("Connection interrupted"); and the miner pasted a session token on
every restart.

### D8. Named refusals at every door

- `supervisor.NEXT_ACTIONS` stays the one closed table. It gains every code
  this part answers or records, and is served as the refusal catalog
  (`supervisor.catalog`, `GET /api/v1/refusals`,
  `carbon.launchpad.refusal-catalog.v1`: `{schema, next_actions,
  fallback}`), so a page renders the next action for any code it meets. An
  error body keeps its one shape on both doors, `{error}` (plus `field` and
  `next_step` for setup, as before); the door-parity tests pin that.
- The HTTP door (`controller.failure_answer`) no longer maps every ValueError
  and RuntimeError to `research_reconciliation_required`: a held lock
  (`controller.LockHeld`, a RuntimeError with the historical message) is
  `campaign_busy`; a typed failure answers its own closed code (an
  `OperationRefused`, a `SignerFailure`); anything else is
  `campaign_readback_unavailable` (reading a campaign), `readback_unavailable`
  (another read) or `operation_not_completed` (a write). Never a message.
- Resume refuses an unreadable profile as `research_profile_unavailable` and a
  stopped campaign as `campaign_stopped`, by name.
- Attaching (`carbon.miner_mcp.standard_cli`) names the check that failed:
  `AttachRefused(code, message)` (a ValueError keeping the historical message)
  where a check refuses, and `_check(code)` marks a foreign failure inside a
  check without changing its type. Codes: `runner_profile_unusable`,
  `research_dispatch_disabled`, `campaign_not_found`, `campaign_complete`,
  `campaign_not_prepared` (no frozen manifest, tasks or session yet),
  `campaign_manifest_differs`, `campaign_revision_differs`,
  `carbon_updated_rerun_installer`, `runtime_unavailable`,
  `campaign_runtime_differs`, `remote_setup_unavailable`,
  `registration_wrong_network`, `miner_differs_from_campaign`,
  `registration_check_failed`, `session_unavailable`, `task_left_running`
  (its next action is the `--cleanup-only` attach), `reconciliation_required`,
  `campaign_stopped`, `campaign_paused` (a granted development campaign
  only), `campaign_busy`; a signer failure keeps its `SignerCode`.
  `carbon-mcp` prints `Carbon MCP unavailable: <code>. <next action>`; the
  open tier still prints its one line. The page's tools route answers the
  same code (`tools_unavailable_for_campaign` when none is named).

### D9. A checkout updated after the installer is named before launch

`runner.checkout_refusal` answers `carbon_updated_rerun_installer` when this
checkout's HEAD is not the profile's `accepted_revision` although the
checkout knows that commit (Carbon was pulled or updated after the installer
wrote the profile), or when the worker or analysis image record the profile
names is not the image its runtime lists (or not built from its source tree).
It is two `git` reads and two small files, cheap enough for every preflight;
the archive digest stays execution's (`accepted_implementation`). What it
cannot judge (a revision this checkout never saw, an unreadable record) is
left to execution, which refuses it by its own check. Preflight then reads
`{available: false, status: CARBON_UPDATED, code, reason}`; launch (before
the registration read), resume, practice, freeze and submit refuse with the
code. A launch already admitted still replays.

### D10. Resume is bound to the frozen campaign

A prepared campaign resumes under any profile that still matches what it was
frozen with (`runner.binding_changes`): principal, accepted revision, images,
the registered hotkey (when the profile's public record is readable) and the
research guidance - exactly what its preparation or run would refuse.
Anything else (the profile's name, model choice for new launches, validator
intakes, the remote machine's address, provider keys for other providers) may
change. When something that matters changed, resume is refused
`profile_changed_since_launch` ("launch a new campaign"); the run's own
guidance check uses the same code. A launch never prepared has no manifest:
it is carried out from its record under the profile its miner reviewed, so
the whole profile still binds it, with the same code (it was
`profile_differs_from_request`, which now names only queue items admitted
under another profile).

### D11. Refused at once, not on the thread

- Submit refuses before anything is admitted when the campaign's Challenge
  is evaluated by a validator (`feedback_schema` set) and the profile
  configures neither a deployment nor an intake for it
  (`runner.evaluation_refusal`: `evaluation_unavailable`). It reads exactly
  what the Challenge's campaign reads when it submits
  (`carbon.battery.campaign.evaluation_config` and `_intake` through
  `campaign_args`; a test pins the equivalence). A deployment that is
  configured but unusable is still refused by the campaign, by its own code.
  Submit also refuses at once a campaign whose agent selects
  (`the_agent_selects_in_this_campaign`) or whose final exams are both used
  (`final_exams_used`), after the state checks.
- Practice, freeze and submit probe the campaign's ownership lock before
  anything is recorded: an attached agent, the page's tools or Carbon's agent
  holding it is `campaign_busy` now; nothing is queued and the idempotency key
  stays unused. The probe holds the lock for an instant; a campaign thread
  starting in that instant retries for up to 1 s
  (`RunnerAdapter.LOCK_WAIT_SECONDS`) rather than answering busy.
- The campaign view's stage that a recorded refusal belongs to (run →
  research, practice, freeze_candidate → candidate, submit) says so: its
  `detail` gains "last attempt <kind>: <code>" and the stage gains
  `refusal: {code, next_action, kind}`.

### D12. Attaching to a paused campaign

A miner's paused campaign can be attached (the MCP attach and the page's
Tools tab). Attaching does not resume it: the pause is lifted for the
attachment, whose ownership lock keeps every other holder out, so its own
research calls are admitted; before it settles on detach the pause is asked
again, so it settles PAUSED. A stop asked while attached stands. A resume the
miner asked for while attached was refused `campaign_busy` (the attachment
held the campaign), so the pause is restored and the miner resumes after
detaching. A granted development campaign keeps the historical rule
(`campaign_paused`). Stopped, complete and reconciliation-required campaigns
are refused by name.

Not in this slice: a paused autonomous campaign's run thread still waits at
its checkpoint holding the lock (`CampaignControl.checkpoint`, handoff), so
while it lives the page's tools answer `campaign_busy_carbon_agent_paused`,
whose text says to restart the Control Center (the campaign stays paused and
the tools then open).

### D13. One campaign never takes the list down

`RunnerAdapter.recent` isolates each campaign: one whose projection fails is
a row `{id, state: READBACK_UNAVAILABLE, mode, next_action}` and the list
(and `GET /api/v1/research`) stays up. Reading that campaign alone answers
`campaign_readback_unavailable`.

### D14. The session link

The Control Center prints `http://127.0.0.1:<port>/#token=<token>`
(`controller.session_url`) beside the token. A fragment is never sent to the
server, logged by it or carried in a Referer. Loopback binding, the Host and
Origin checks, the bearer token on every API call and the CSP are unchanged.
The page reading the fragment once, removing it from the address bar before
anything stores the route, is slice F's.

**Contract additions (for slices F and B).** `GET /api/v1/refusals` (D8);
preflight `status: CARBON_UPDATED` with `code` (D9); campaign-view stage
`refusal` (D11); list row `next_action` for READBACK_UNAVAILABLE (D13); the
new codes above; busy hint `carbon_agent_paused`. `last_refusal`, `in_flight`
and `recovery` are unchanged from D7.

**Tests.** `tests/cpu/test_launchpad_truthful_refusals.py` (new) and new cases
in `tests/service/test_standard_mcp_cli.py`. Deliberately changed
assertions: a held lock is now refused before the thread starts, so
