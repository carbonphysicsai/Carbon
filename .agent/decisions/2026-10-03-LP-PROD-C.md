## 2026-10-03 — LP-PROD-C: one campaign supervisor, and campaign state that tells the truth

**Authority.** Delegated engineering decisions (executor), within
OWNER-LAUNCHPAD-PROD-01: the owner's instruction of 2026-10-03 to make the
miner front end zero-friction and production-level, and the owner's approval
of the Launchpad production work list in session ("approve. you launch this
now"). Slice C of that list: the campaign supervisor and truthful state.
Nothing here changes a scientific value, threshold, gate or tolerance, live
economics or a default spend value, any chain write or weight, what a host
exposes, or any key-holding boundary. DEVELOPMENT evidence only.

**Why.** Observed live on 2026-10-03 and confirmed in the code at `4be2642`:
1. A launch, practice, freeze or submit ran on a daemon thread of whichever
   process received it, including a short-lived MCP stdio process. When that
   client exited the thread died: the campaign stayed QUEUED with no
   `campaign-manifest.json`, and attaching to it failed ("private bounded
   operator record required").
2. `RunnerAdapter.close` sent an irreversible stop to every live thread, so
   closing an agent mid-practice stopped its campaign for good.
3. Every start of the Control Center or of `carbon-mcp --configuration`
   settled every campaign not COMPLETED, STOPPED or PAUSED with cleanup
   assumed failed, which flagged idle READY campaigns RECONCILIATION_REQUIRED.
   Resuming a launch never prepared started a run with no product, which is
   the retired grant path.
4. Pause or Stop on a campaign nothing was running stayed PAUSE_REQUESTED or
   STOPPING for ever, and Resume was disabled for PAUSE_REQUESTED.

### D1. Who runs campaign threads

`scripts/dev/miner_launchpad/supervisor.py` defines four roles for the one
campaign host (`RunnerAdapter`):
- **SUPERVISOR**: the Control Center, while it runs. It runs its own
  requests' threads and drains what clients queue.
- **DETACHED**: when no Control Center is running, a client that queues work
  and finds no supervisor alive starts
  `python -m scripts.dev.miner_launchpad.supervisor --configuration PROFILE`
  with `start_new_session` (detached process flags on Windows), its standard
  streams on the null device so it never writes to an MCP client's stdio. It
  exits once nothing is queued and none of its threads is still working for
  10 s. A run parked at its campaign's checkpoint while the campaign is
  paused (settled PAUSED, nothing reserved or held) does not count as
  working: a Resume carries it on with a new run, anywhere, so exiting loses
  nothing (review repair; before it, one paused autonomous campaign kept the
  process alive for as long as it stayed paused).
- **CLIENT**: every MCP door (`for_profile`'s default). It runs the
  operations table's gates, queues what was admitted, wakes or starts the
  supervisor, and observes. It never owns a campaign thread.
- **INLINE**: the historical single-process behaviour, for fixtures and tests
  that drive a host directly. No production door constructs it.

Exactly one supervisor holds the lock for a runner database and principal: an
OS lock (`controller.owner_lock`) in `.supervisor-<digest>` beside the
database, released by the OS when its process exits. Only the holder starts
queued work or recovers campaigns. Every campaign's own ownership lock is
unchanged: one holder per campaign.

**The handover (review repair).** A Control Center that starts while a
detached supervisor holds the lock becomes the supervisor; until this repair
it stayed a client for as long as that process lived, so its own work ran
there and closing it paused nothing. The Control Center holds a second OS
lock, its presence (`.supervisor-<digest>/control-center`), for as long as it
runs. A detached supervisor that sees it:
- starts nothing more (queued work waits for the Control Center);
- asks Carbon's agent in each prepared campaign it runs to pause, recording
  `paused_for_handover`. The agent stops at its next checkpoint, between
  bounded operations, so a model call or training run already under way
  finishes first;
- lets everything else it runs finish: a launch still being prepared, or a
  miner's practice, freeze or submit. Nothing is cut off;
- once nothing of its own is working (parked runs excepted, D1), releases
  the lock and exits.

The Control Center then takes the lock, recovers (D5), and resumes each
campaign still paused for the handover (ledger PAUSED, desired PAUSE, last
refusal `paused_for_handover`), exactly as a Resume would, with the same
refusals. It does this on each of its passes, and only once that campaign's
own lock is free. The agent's run, parked in the detached process, holds that
lock until the process exits. A resume asked before then would wake the run
in a process about to end, and cut off whatever it started next. A campaign
whose miner paused it stays paused. Only a Control Center
resumes a handover pause. A detached supervisor that takes the lock with no
Control Center running, or that sees the Control Center go before it took
over, keeps those campaigns paused and re-records them
`paused_when_supervisor_closed` (D4). A detached supervisor started while a
Control Center runs exits at once.

### D2. The dispatch queue

`launchpad_dispatch`, in the runner's own database (owner-only): what a client
admitted, as QUEUED → RUNNING (claimed by one supervisor) → DONE. A claimed
item is never started twice. A RUNNING item whose supervisor died is marked
`interrupted` and never replayed: the campaign's ledger, not the queue, says
what may have been dispatched, so no paid model call with an unknown outcome
is resent. The one case recovery carries out again is a launch that died
before it was prepared and has nothing outstanding (D5). That runs as a new
item, once. The supervisor reads the runner profile again and refuses an item
admitted under a different profile (`profile_differs_from_request`); it never
runs one profile's request under another. A QUEUED item no supervisor has
claimed can be withdrawn (outcome `withdrawn`, D4); a claimed one cannot.

### D3. A launch carried out where it was not received

A launch now records its admitted request (`launchpad_campaigns.launch_request`,
without the idempotency key). A run that must create the campaign and holds no
in-memory admission (a supervisor in another process, or a restart before the
campaign was prepared) rebuilds the `ProductLaunch` from that record:
- the record must reproduce the recorded identity and request digest
  (`launch_record_differs`) under the same profile
  (`profile_differs_from_request`);
- its Challenge, model choice and budget are validated again exactly as at
  launch;
- registration is read again, with the signer probe, because a
  `RegisteredMiner` can only be built by a read and the one that admitted the
  launch lived in the receiving process. The frozen manifest therefore
  records the observation the campaign actually started under; downstream
  only its hotkey is compared, and it cannot differ.
- A row recorded before this decision has no record and is refused by name
  (`launch_choices_unrecorded`: stop it and launch again). Nothing ever runs
  with no product again.

### D4. Closing pauses or detaches, never stops

Closing a client changes no campaign (its attachment, if any, is detached as
before). Closing a supervisor asks each campaign with a live thread to pause,
records `paused_when_supervisor_closed`, waits up to 5 s for each thread to
end or park at the pause (a parked run never ends on its own; waiting for it
only delayed the next supervisor), and releases the supervisor lock. One that
does not settle in time is settled from its ledger by the next supervisor's
recovery (PAUSED, or RECONCILIATION_REQUIRED if work may be outstanding).
Closing the Control Center does not hand running campaigns to a detached
supervisor: that would keep model and compute spend running after the miner
closed their surface. Pause is the conservative, one-call-reversible choice;
see Owner decisions. Work still QUEUED when a supervisor closes waits for the
next supervisor; a client that observes it with none alive starts one (at most
one per 3 s).

The same holds for a Control Center that closes before it took over from a
detached supervisor (review repair). Before this, its work ran on unattended
in the detached process, which in effect took the open owner decision below
without the owner. What it admitted meanwhile:
- not yet claimed by any supervisor: withdrawn. A launch or resume leaves
  its campaign paused (`paused_when_supervisor_closed`, operation `run`;
  Resume carries it out). A practice, freeze or submit never ran and is
  `withdrawn_when_supervisor_closed`: send it again. The campaign is not
  paused for it.
- already started elsewhere: asked to pause.
- paused for the handover: stays paused (`paused_when_supervisor_closed`).

Once the Control Center has taken over, a campaign it now supervises is
paused on close like any other, wherever the campaign was launched (an MCP
agent's included).

### D5. Recovery

Run by the supervisor when it takes the lock (INLINE: at construction, never
re-dispatching). For each campaign whose ownership lock is free:
- settled campaigns (READY, PAUSED, INTERRUPTED, COMPLETED, STOPPED,
  RECONCILIATION_REQUIRED) are left exactly as they are;
- a campaign whose ledger still says a process was working (QUEUED,
  RECONCILING, RUNNING, PAUSE_REQUESTED, RESUME_REQUESTED, STOPPING) is
  settled with the real cleanup check (`RunnerAdapter._cleanup`):
  RECONCILIATION_REQUIRED only when work may be outstanding or cleanup is not
  verified, otherwise READY (the miner selects and nothing was asked),
  INTERRUPTED, PAUSED or STOPPED as asked;
- one with queued work and nothing outstanding is left to that work, so it is
  not reported interrupted first;
- a launch admitted and never prepared (row QUEUED, no frozen manifest, its
  choices recorded, nothing queued, not paused, stopped or awaiting
  reconciliation, and no refusal recorded before this recovery) is queued
  again as a new item and carried out with its recorded choices (D3). This
  is the live failure's own case: the process carrying a launch died before
  preparing it. Nothing can have been dispatched for it, since there is no
  manifest and recovery found nothing outstanding. The interruption recovery
  recorded a moment earlier is cleared as it is queued, so the campaign does
  not read as interrupted while it runs. This happens once only: a launch
  whose run is interrupted again (`interrupted_runs` > 1) keeps
  `campaign_interrupted` and waits for its miner's Resume, because
  preparation itself may be what ends the process. A launch refused before
  this recovery also waits for Resume. (Review repair: the re-dispatch check
  read the refusal from a row read before recovery recorded it, so an
  orphaned launch was re-queued however often it was orphaned, and reached
  READY still reading `campaign_interrupted`. The check still uses that
  earlier row, on purpose, and the recorded interruption is now cleared.)
- a run settled PAUSED keeps the reason it was paused (its supervisor
  closed, a handover) rather than being re-told it was interrupted;
- an operation a dead process left at a pause (ledger PAUSED, its item
  RUNNING) never dispatched, so it is reported `operation_interrupted` (send
  it again) rather than silently lost.

The work list's "skip campaigns with no RESERVED/HELD operations" is read as:
settled campaigns are skipped, and a campaign left mid-flight with nothing
outstanding is settled by the real check rather than left reading RUNNING with
nothing running.

### D6. Idle controls settle at once

Pause, Stop and Reconcile take the campaign's ownership lock without waiting:
if it is free nothing will ever act on the request, so it is settled now with
the real cleanup check (PAUSED, STOPPED, or for Reconcile READY or
INTERRUPTED; RECONCILIATION_REQUIRED while work may be outstanding). If a live
holder has it, Pause and Stop stay requested for that holder's next
checkpoint, and Reconcile is refused `campaign_busy`. Resume is offered for
PAUSE_REQUESTED (it cancels a pause not yet settled) and for a stranded QUEUED
launch.

To keep that true:
- practice, freeze and submit are refused at once on a campaign not yet
  prepared, complete, stopped, paused or awaiting reconciliation, by name;
- an operation, like a run already did, never starts over RESERVED or HELD
  work (`unresolved_operation`, to reconciliation);
- a run or operation that ends while a pause or stop was asked settles
  PAUSED or STOPPED, not READY (`CampaignControl.settled` ranks READY above a
  pending pause);
- an operation refused before dispatch, including a credential refusal,
  settles the generation it took instead of leaving it RECONCILING;
- detaching an agent-less campaign settles it READY, not INTERRUPTED
  (`standard_cli._waits_for_its_miner`).

### D7. The published contract: `last_refusal`, `in_flight`, `recovery`

The observe document (`RunnerAdapter.get`: the `observe` operation, the
browser's `/api/v1/research/<id>` and every list row) and the campaign view
(`carbon.control-center.campaign-view.v1`, additive) gain:
- `last_refusal`: `{code, next_action, at, operation, kind}` or null. `code`
  is a closed identifier (`[a-z][a-z0-9_]{0,63}` or upper case); any other
  is recorded as `operation_refused`, never echoed. `next_action` comes from
  `supervisor.NEXT_ACTIONS`; a code it does not list (a new validator intake
  code, say) is shown with `FALLBACK_ACTION`, so it reaches the miner before
  the table names it. `at` is Unix seconds. `operation` is `run`,
  `practice`, `freeze_candidate`, `submit` or null. `kind` is `refused`
  (nothing dispatched), `interrupted` or `paused`. It is set only where no
  caller was waiting (on a supervisor thread, or by recovery), and cleared
  when the next attempt is admitted. A refusal returned to the caller stays
  the caller's error and is not recorded.
- `in_flight`: `{operation, state (QUEUED or RUNNING), since,
  supervisor_running}` or null.
- `recovery`: `[{action, operation}]`: `resume`/`resume`, `stop`/`halt`,
  `reconcile`/`halt`; empty when nothing is needed. Only what can succeed:
  a retired-grant campaign or one on a retired Challenge, whose resume is
  always refused, is never offered resume (review repair).

Carbon's agent selecting a candidate the validator did not evaluate is
reported the same way: `run_agent` and `execute` now return that refusal's
code (`research_campaign`), and the run records it with operation `submit`.
The decision note the agent path writes, and every frozen rule, prompt and
digest, are unchanged.

**Tests.** `tests/cpu/test_launchpad_supervisor.py` (new) covers each
decision. Deliberately changed assertions: an idle Stop now reads STOPPED
(`test_stop_and_retained_readback_need_no_chain_read`,
`test_a_retired_grant_campaign_stays_readable_and_stoppable`), and an
agent-less campaign is READY after its client detaches
(`test_actual_gateway_public_workflow_and_restart_over_stdio`).

### D8. Named refusals at every door

- `supervisor.NEXT_ACTIONS` stays the one closed table. It gains every code
  this part answers or records, and is served as the refusal catalog
  (`supervisor.catalog`, `GET /api/v1/refusals`,
  `carbon.launchpad.refusal-catalog.v1`: `{schema, next_actions,
  fallback}`), so a page renders the next action for any code it meets.
- An error body on the HTTP door is `{error}`, plus `next_step` when the
  catalog names the code (`controller.error_body`, review repair: a
  synchronous refusal such as `evaluation_unavailable` came with no next
  action at either door, and the catalog alone needed every client to fetch
  it first). A setup refusal still carries its own `field` and `next_step`.
  `next_step` is the name setup refusals and slice B's MCP refusal body
  (`operations.refusal`) already use; the step is the catalog's fixed text,
  never anything from the request or the failure. The door-parity tests now
  pin `{error, next_step}` for a catalog code.
- The HTTP door (`controller.failure_answer`) no longer maps every ValueError
  and RuntimeError to `research_reconciliation_required`: a held lock
  (`controller.LockHeld`, a RuntimeError with the historical message) is
  `campaign_busy`; a typed failure answers its own closed code (an
  `OperationRefused`, a `SignerFailure`, and a campaign whose own records
  disagree: `projection.RecordsDiffer`, `campaign_readback_unavailable`);
  anything else is `campaign_read_failed` (reading a campaign: "reload; if it
  persists, restart the Control Center", review repair: it used to advise
  launching a new campaign for what may pass), `readback_unavailable`
  (another read) or `operation_not_completed` (a write). Never a message.
- Resume refuses an unreadable profile as `research_profile_unavailable` and a
  stopped campaign as `campaign_stopped`, by name.
- Attaching (`carbon.miner_mcp.standard_cli`) names the check that failed:
  `AttachRefused(code, message)` (a ValueError keeping the historical message)
  where a check refuses, and `_check(code)` marks a foreign failure inside a
  check without changing its type. Codes: `runner_profile_unusable`,
  `research_dispatch_disabled`, `campaign_not_found`, `campaign_complete`,
  `campaign_not_prepared` (no frozen manifest, tasks or session yet),
  `campaign_manifest_differs`, `campaign_revision_differs`,
  `carbon_updated_rerun_installer`, `runtime_unavailable`,
  `campaign_runtime_differs`, `remote_setup_unavailable`,
  `registration_wrong_network`, `miner_differs_from_campaign`,
  `registration_check_failed`, `session_unavailable` (no prepared session
  yet), `campaign_owner_changed` (the signer authenticates as another owner
  than the campaign's: resuming cannot fix it, review repair),
  `task_left_running` (its next action is the `--cleanup-only` attach),
  `reconciliation_required`, `campaign_stopped`, `campaign_paused` (a granted
  development campaign only), `campaign_busy`; a signer failure keeps its
  `SignerCode`. A miner public record without `netuid` or `hotkey` is
  `runner_profile_unusable`, not the `runtime_unavailable` of the check
  around it (review repair).
  `carbon-mcp` prints `Carbon MCP unavailable: <code>. <next action>`; the
  open tier still prints its one line. The page's tools route answers the
  same code (`tools_unavailable_for_campaign` when none is named).

### D9. A checkout updated after the installer is named before launch

`runner.checkout_refusal` answers `carbon_updated_rerun_installer` when this
checkout's HEAD is not the profile's `accepted_revision` although the
checkout knows that commit (Carbon was pulled or updated after the installer
wrote the profile), or when the worker or analysis image record the profile
names is not the image its runtime lists (or not built from its source tree).
It is two `git` reads and two small files, cheap enough for every preflight;
the archive digest stays execution's (`accepted_implementation`). What it
cannot judge (a revision this checkout never saw, an unreadable record) is
left to execution, which refuses it by its own check. Preflight then reads
`{available: false, status: CARBON_UPDATED, code, reason}`; launch (before
the registration read), resume, practice, freeze and submit refuse with the
code. A launch already admitted still replays.

### D10. Resume is bound to the frozen campaign

A prepared campaign resumes under any profile that still matches what it was
frozen with (`runner.binding_changes`): principal, accepted revision, images,
the registered hotkey (when the profile's public record is readable) and the
research guidance - exactly what its preparation or run would refuse.
Anything else (the profile's name, model choice for new launches, validator
intakes, the remote machine's address, provider keys for other providers) may
change. When something that matters changed, resume is refused
`profile_changed_since_launch` ("launch a new campaign"); the run's own
guidance check uses the same code. A launch never prepared has no manifest:
it is carried out from its record under the profile its miner reviewed, so
the whole profile still binds it, with the same code (it was
`profile_differs_from_request`, which now names only queue items admitted
under another profile).

### D11. Refused at once, not on the thread

- Submit refuses before anything is admitted when the campaign's Challenge
  is evaluated by a validator (`feedback_schema` set) and the profile
  configures neither a deployment nor an intake for it
  (`runner.evaluation_refusal`: `evaluation_unavailable`). It mirrors what
  the Challenge's campaign reads when it submits
  (`carbon.battery.campaign.evaluation_config` and `_intake` through
  `campaign_args`) rather than importing them: the runner names no
  Challenge's own module (`test_control_center_challenge_neutral`). Two
  tests hold the mirror to them: the same answer for every profile shape,
  and a recording test that fails as soon as the battery campaign reads an
  argument the mirror does not know. A deployment that is configured but
  unusable is still refused by the campaign, by its own code.
  Submit also refuses at once a campaign whose agent selects
  (`the_agent_selects_in_this_campaign`) or whose final exams are both used
  (`final_exams_used`), after the state checks.
- Practice, freeze and submit probe the campaign's ownership lock before
  anything is recorded: an attached agent, the page's tools or Carbon's agent
  holding it is `campaign_busy` now; nothing is queued and the idempotency key
  stays unused. The probe holds the lock for an instant. A campaign thread
  starting in that instant retries for up to 1 s
  (`RunnerAdapter.LOCK_WAIT_SECONDS`) rather than answering busy. Other
  takers that do not retry can still lose to a probe in that instant: an
  attach or the page's tools (answered `campaign_busy`; try again), an idle
  Pause or Stop (left requested, and settled by the next recovery or
  control), a Reconcile (`campaign_busy`), and recovery (the campaign is
  settled by the next one). These races are rare and recoverable, and
  giving each a retry window would delay every Pause on a running campaign
  by that window. (Review: the claim was narrowed to campaign threads.)
- The campaign view's stage that a recorded refusal belongs to (run →
  research, practice, freeze_candidate → candidate, submit) says so: its
  `detail` gains "last attempt <kind>: <code>" and the stage gains
  `refusal: {code, next_action, kind}`.

### D12. Attaching to a paused campaign

A miner's paused campaign can be attached (the MCP attach and the page's
Tools tab). Attaching does not resume it: the pause is lifted for the
attachment, whose ownership lock keeps every other holder out, so its own
research calls are admitted; before it settles on detach the pause is asked
again, so it settles PAUSED. A stop asked while attached stands. A resume the
miner asked for while attached was refused `campaign_busy` (the attachment
held the campaign), so the pause is restored and the miner resumes after
detaching. A granted development campaign keeps the historical rule
(`campaign_paused`). Stopped, complete and reconciliation-required campaigns
are refused by name.

Not in this slice: a paused autonomous campaign's run thread still waits at
its checkpoint holding the lock (`CampaignControl.checkpoint`, handoff), so
while it lives the page's tools answer `campaign_busy_carbon_agent_paused`.
That is also the answer when the parked run is in a detached supervisor
(review repair: that case said "pause Carbon's agent", which was already
done). There it ends within seconds, because a detached supervisor hands
over to a running Control Center and no longer stays alive for a parked
run (D1). Only a run parked in the Control Center itself needs the restart
the text names. The campaign stays paused either way, and the tools then
open.

### D13. One campaign never takes the list down

`RunnerAdapter.recent` isolates each campaign: one whose projection fails is
a row `{id, state: READBACK_UNAVAILABLE, mode, code, next_action}` and the
list (and `GET /api/v1/research`) stays up. `code` is
`campaign_readback_unavailable` when its records disagree
(`projection.RecordsDiffer`), and `campaign_read_failed` for any other
failure, which may pass (review repair). Reading that campaign alone answers
the same code.

### D14. The session link

The Control Center prints `http://127.0.0.1:<port>/#token=<token>`
(`controller.session_url`) beside the token. A fragment is never sent to the
server, logged by it or carried in a Referer. Loopback binding, the Host and
Origin checks, the bearer token on every API call and the CSP are unchanged.
The page reading the fragment once, removing it from the address bar before
anything stores the route, is slice F's.

The link is printed only once the page declares, in its own `<head>`, that
it reads the fragment: `<meta name="carbon-session-link"
content="fragment-v1">` (`controller.session_link_supported`). Until then
the Control Center and `research_demo` print the address and the bare token,
as before. (Review repair: today's page stores `location.hash` into its saved
route, so opening the link before slice F lands would keep the token in
localStorage and history without connecting.) This cannot ship ahead of the
page in either merge order.

## 2026-10-03 — W1 (integration wiring): the refusal catalog is the one source of next steps, and names the intake's codes

**Authority.** Delegated engineering decisions (integration fixer W1), within
OWNER-LAUNCHPAD-PROD-01. Text and wiring only: nothing here changes a
scientific value, live economics, a default spend, a chain write or weight, a
host's exposure or an authority boundary.

1. *One catalog for both doors (B<->C).* `NEXT_ACTIONS` now holds the step
   for every closed code either door answers: the operations table's own
   refusals that LP-PROD-B kept in a second table, the body refusals neither
   table named (`bounded_hypothesis_required`, `design_<verdict>`,
   `unknown_experiment`, ...) and the MCP attach refusals. `operations.refusal`
   adds only the field (`REFUSAL_FIELDS`). Where both tables had a code, C's
   step is kept and gains the MCP tool B named, in parentheses
   (`carbon_onboarding_prepare`, `carbon_setup_status`,
   `carbon_setup_inference`, `carbon_freeze_candidate`). `next_action(code)`
   is the one lookup. The browser's `closed_request_required` now carries its
   step; `unknown_operation` (a browser-only 404) stays unnamed.
2. *Every closed code a submission through an intake can end with has its
   own step (G->C).* `campaign.intake_code` maps every intake and transport
   answer into `intake_client.REFUSALS`; each of those codes - the intake's
   (`rate`, `hotkey_window_used`, ...), its transport's and signature
   checks' (`TRANSPORT_*`, `AUTH_*`) and the trip's own (`intake_mismatch`,
   `intake_signer_changed`, `signer_unavailable`,
   `intake_changed_since_submission`, `intake_answer_unrecognised`) - now has
   a step written for a Launchpad submit: what happened, that the frozen
   candidate is kept, and what to do (wait, check the intake address or the
   signer, commit, submit again). `last_refusal` no longer falls back for them.
   Not covered: the local deployment path's configuration codes
   (`evaluation_config_*`, `evaluation_<state>`), which take the fallback as
   before.

Tests: `tests/cpu/test_lp_prod_wire_doors.py` (every intake code has its own
step; the intake path reports only those codes; the catalog's steps are what
the MCP door sends); `test_an_error_body_carries_the_catalogs_next_step_only`
now uses `unknown_operation` as its unnamed code; journey scenarios 6a and 6c.

### 2026-10-03 — LP-PROD-W2: Reconcile settles a model call whose outcome is unknown

**Why.** Integration testing (journey scenario 5b) found that nothing called
LP-PROD-A's settlement (`research_agent.settle_uncertain_calls`). A's part 2
decision 4 names the reconcile action as its entry point, but `_cleanup`
reconciles worker operations only. So a campaign whose model call timed out,
lost its connection or got a 500 stayed RECONCILIATION_REQUIRED for ever.

**Decision.** Delegated engineering, within OWNER-LAUNCHPAD-PROD-01.
- The miner's Reconcile (`_control("reconcile")` → `_settle_if_idle(reconciling=True)`)
  settles every model call of the manifest owner whose outcome is unknown,
  under the campaign's owner lock and the generation it has just taken
  (observed RECONCILING), before the cleanup check
  (`research_campaign.reconcile_model_calls` over A's function). A's fences
  and refusals apply unchanged (`call_in_flight`, `control_fenced`, a charge
  or usage the ledger cannot book). Each call is booked at its full
  reservation and journalled. Nothing is resent; the next resume sends the
  same request under a fresh identity.
- Pause, stop and recovery never settle a model call.
- A refused settlement leaves the call RESERVED and the campaign awaiting
  reconciliation. Reconcile answers the first refused call's closed code
  (`SETTLEMENT_REFUSALS`) with A's next step for it, as `next_step` on the
  `Rejected` (the HTTP body carries it through `error_body`). An unexpected
  failure while settling answers `operation_not_completed`, after the
  campaign is settled as it stands.
- Readback, additive. The observe document gains `unknown_outcome_calls`:
  `settled` (`identity`, `reason`, `booked_nanodollars`, `caveat`),
  `awaiting_settlement` (`identity`, `booked_on_settlement_nanodollars`;
  listed only while RECONCILIATION_REQUIRED) and `accounting`. It is read
  from the ledger alone: observing takes no lease, so it never races a
  Reconcile into `call_in_flight`. The campaign view gains
  `reconciliation`, null when there is nothing. A settled call's booked
  charge counts under `usage.uncertain`, not `usage.reported`; the totals
  are unchanged.
- The development CLI gains `research_campaign reconcile --root R`: the same
  settlement for its own uncontrolled campaign, printing the report, exit 1
  on any refusal. A controlled campaign is refused `control_fenced` and
  nothing is settled: only its own reconcile action holds its owner lock and
  generation.

**Unchanged.** No automatic settlement and no blind resend; the accounting
rule (the full reservation); A's refusals and fences; every frozen plan,
prompt and digest. DEVELOPMENT only.

**Handoffs.** The MCP door answers a runner `Rejected` through
`operations.refusal(code)`, which gives these codes the generic step; it
should prefer the exception's own `next_step` (B). The page should render
`reconciliation` (F).

**Tests.** `tests/cpu/test_lp_prod_wire_runtime.py`; journey scenario 5b.

### 2026-10-03 — Review repairs of the wiring (repair round): one step per refusal at both doors

**Authority.** Delegated engineering decisions (repair executor), within
OWNER-LAUNCHPAD-PROD-01. Text and wiring only; nothing scientific, economic,
chain-facing or security-relevant changes.

1. *A refusal's own step crosses both doors (closes W2's B handoff).* The
   HTTP door sent a stepped `Rejected`'s `next_step` (`error_body`); the MCP
   door read only the catalog. So `carbon_halt action=reconcile` answered
   A's settlement refusals with `FALLBACK_ACTION` (for `call_in_flight`, and
   for `charge_exceeds_reservation` it hid A's instruction to reconcile
   against the provider's usage record first), and `carbon-mcp` told a stale
   profile "re-run the installer" where a compute check and Review clear it.
   Now `operations.refusal(code, next_step)` takes the refusal's own step,
   and `mcp_operations` passes `getattr(exc, "next_step", None)`, exactly as
   `error_body` reads it; `standard_cli.unavailable_message` prints a
   `Rejected`'s own step as `Next: <step>.`. The catalog also names A's eight
   settlement codes (`SETTLEMENT_REFUSALS`), each A's step as a sentence, so
   a `last_refusal` and `GET /api/v1/refusals` no longer fall back for them.
   Deliberately changed assertion: `test_carbon_mcp_never_attaches_a_stale_profile`
   now expects the computed step (the one the HTTP door sends), not the
   catalog's.
