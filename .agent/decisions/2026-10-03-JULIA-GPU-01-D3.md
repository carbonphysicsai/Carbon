## 2026-10-03 — JULIA-GPU-01-D3: a real CUDA kernel through the miner lane, and the lane's own GPU allocation record

**Authority.** OWNER-EXEC-APPROVALS-01 item 4 ("GPu Julia"), slice 3 of
`.agent/tickets/JULIA-GPU-01_cuda_julia_depot.md`. The miner-lane cleanup
change touches GPU container cleanup (AGENTS.md §13). It was put to the
owner, who approved it in chat on 2026-10-03 ("i approve it").

**Decision.**
1. **The miner lane records its GPU allocation.** The first real run found
   the defect. The lane labelled its container with the device but recorded
   no allocation.
   - Removing a device-labelled container completes the allocation that
     created it. With none recorded, removal took the strict path, which
     requires verified whole-device release, and refused
     (`WorkerFailure(CLEANUP)`) after every real GPU run.
   - The same was true of `run_python` on GPU (RSURF-D20). Its tests replace
     removal with a double, so CI never saw it.
   - `_run_miner_lane` now records the allocation before create, under the
     shared slot. It uses the miner lane's own task-owned authority
     (`MINER_HOST_SELF_SERVICE`), as GPU practice already does through the
     controller.
   - Cleanup completes it with `finish_local_device_allocation`. That removes
     the record and never claims whole-device release, which the lane never
     had the evidence for.
   - The strict path is unchanged. Neither authority can complete the
     other's record.
   - Validator GPU work now sees this run's record from before create, not
     only its device label after it.
2. **The kernel run is a GPU-host test.** `tests/service/test_julia_gpu_lane.py`
   runs a CUDA kernel through `run_julia` on the miner's GPU. It checks the
   result against the host's own arithmetic and times a first and a second
   kernel. It is skipped wherever no host device record is installed, which
   includes CI.
3. **Host floor, unchanged from D1.** The NVIDIA driver must support CUDA
   13.0 natively, because the bundled compatibility driver is disabled. That
   is the 580 series or later, on Turing or newer. The driver observed here
   was 581.95.

**Measured.** 2026-10-03, WSL2, an RTX 3060 Laptop GPU (compute capability
8.6), driver 581.95. Self-reported by the miner, speed only.
- CUDA is functional, and the GPU's sum matches the host's. The driver API
  and the runtime are both 13.0.
- **First kernel: 3.9 s.** That covers CUDA initialization and compiling the
  broadcast and the reduction; an earlier run took 4.4 s. **Second kernel:
  0.20 s.**
- **Whole operation: 12.1 s.** That covers container create and start,
  loading CUDA, the kernels, output collection and verified removal.
- **First run on a host.** The first test run here took 555 s in total,
  including composing the campaign's Julia image from the adopted depot.
  Later runs reuse the composed image.

**Not run.** `run_python` on a real GPU. It goes through the same fixed lane,
and the new unit test covers the record and its completion. No Python GPU
worker image is installed on this host.

**Unchanged.**
- The validator stays on jax-cpu. Julia analysis stays
  `official_eligible: False`.
- GPU practice and the GPU code cell are speed only, never evidence.
- Nothing is security-qualified (OWNER-EXEC-APPROVALS-01 item 3; AGENTS.md
  §13). The cleanup change and its tests are engineering evidence, not a
  security review.
