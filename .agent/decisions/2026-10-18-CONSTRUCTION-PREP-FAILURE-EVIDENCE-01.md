# Fixed preparation failure observations

Root delegates this bounded engineering repair in the common construction lane. PROGRAM failure currently bypasses normal resource observation before owned container cleanup. Classify that seam as IMPLEMENTATION_LAG; exit status alone does not establish an OOM or scientific failure.

Capture owner-private fixed-PREP container/cgroup observations immediately before PROGRAM and, best effort, on PROGRAM failure before normal cleanup. Inspect only the exact expected launch and image, read a closed bounded memory counter set, and use at most two Docker reads within a one-second absolute observation budget. The baseline consumes the existing phase budget; it adds no allowance. Retain only fixed primitive metadata under the existing private operation, with UNKNOWN for absent, malformed, mismatched or unavailable observations. A false PID1 OOM flag cannot exclude an exec-process OOM.

Retain exact owned-cancellation and deadline-watchdog cleanup requests at their existing action points. A request record is not proof of successful termination or of the failure's cause. Optional watchdog evidence must verify the existing immutable operation intent; legacy watchdog invocations keep their original behavior. Observation/write failure must not replace the original error or prevent cleanup.

No CPU, memory, swap, wall, filesystem, network, admission, retry or public-disclosure policy changes. No participant code or submitted fitted state enters evaluation. This produces DEVELOPMENT engineering evidence only, without scientific or security qualification. Dedicated source review and focused canonical tests remain required. Product owns actual cleanup/resources and one finite normal signed CR01 run after the focused checks and scoped review, using the already-corrected packet and matching source/image/profile. Root explicitly authorized that instrumented run to establish the cause or earn real rebuild, inference and retention evidence; recovering the old R3 kill cause is not a prerequisite.

After the first authentic normal model succeeds, the existing service/matrix harness will measure the owner's100-plus-rebuilds-per-day reliability target with finite cold/warm dependency reuse, fresh model state, restart/recovery, explicit infra retry and bounded concurrency. Duplicate/cached model responses do not count as rebuilds. No batch or performance claim is authorized by this decision.
