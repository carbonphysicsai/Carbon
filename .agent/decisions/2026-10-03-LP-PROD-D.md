## 2026-10-03 — LP-PROD-D: research tools as the model experiences them

**Authority.** Delegated engineering decisions (executor), within
OWNER-LAUNCHPAD-PROD-01: the owner's 2026-10-03 instruction to make the miner
front end zero-friction, production-level and state of the art, and the
owner's approval of the work list in chat on 2026-10-03 ("approve. you launch
this now"). Nothing here changes a scientific value, threshold, gate or
tolerance, live economics, a default spend, a chain write or weight, an
authority boundary or the security posture. Every result stays DEVELOPMENT
and MINER_SELF_REPORTED where it was.

**Why it is needed.** A workspace request with a bad *value* (a material name
outside the list, a stale `expected_digest`, a missing file, a run without a
wall allowance under a time budget, a design with an extra key) passed the
field check, started a task and ended FAILED_INFRA. The agent saw no reason:
the model's view drops the terminal receipt. Run results returned only
digests, so the agent could not see its own program's output or traceback.
Battery's roadmap and capability requests read Burgers' registry. The battery
discovery text described tools the agent does not have and examples that
`check_design` refuses.

**Decisions.**

1. **One value check, read before dispatch and at execution.**
   `research_tasks.check_workspace_request` is the one rule. The request path
   (`ResearchMinerTools._check_values`) reads it before anything is reserved,
   so a refused value starts no task, charges no research-trial slot and
   returns REJECTED_BEFORE_DISPATCH with a closed `correction_code`, the
   registered `field` and the fix. The executor reads it again before it
   acts. A request that reaches it anyway (a raw protocol client, or a
   workspace changed in between) completes as SUCCEEDED with
   `outcome: REQUEST_REFUSED` and the same three fields, `nothing_ran: true`,
   `trial_charged: false`. That is never FAILED_INFRA: the requester's value
   is not an infrastructure failure, the precedent `MINER_PROGRAM_FAILED`
   set. The historical exception text is kept, so a caller that only knew
   ValueError reads what it always read.
   - Codes added to `research_tools.TASK_CORRECTIONS`: public material, read
     range, workspace name, missing file, write content, expected-digest
     conflict (the correction explains what `expected_digest` is), notebook
     kind and reserved body, capability request object, missing and
     unexpected fields, reason, text bound and unknown id, the three
     `check_design` shapes, run hypothesis, source, files, seconds and
     required seconds, Julia environment, `backend_not_served`, unknown
     workspace action, oversized arguments, and the tool-level codes in
     decision 7.
   - Checks that read state (a file exists, a write's expected digest, the
     compute-time budget) are skipped when this operation id already started
     a task (`InMemoryResearchTaskProvider.started_task`, a trusted lookup).
     A resend then returns that task, and is never refused for a guard its
     own run moved.
   - The audit said `lifecycle.py` runs such a task three times. That holds
     only for the in-memory fixture provider. The real
     `DurableResearchTaskProvider` wraps the executor in `_NoRetry`, so the
     task failed once, without a reason. The retry policy is unchanged; the
     value never reaches it now.
   - A run's reserved stage names are its own carrier's: `program.py` for
     every run, and `program.jl` too for `run_julia`
     (`research_tasks.reserved_stage_names`). A `run_python` may stage an own
     file named `program.jl`, as it always could.
   - A capability request's `reason` sent as a list or object is named as
     `capability_request_reason_unknown`, not refused unnamed.
   - **The standard MCP door must forward these refusals.** Its result check
     (`carbon/miner_mcp/standard.py` `_result`, slice B's file) accepts a
     correction only for `start_research_task`, only without `field`, and
     only as the bare registered text. A named refusal - already on
     `origin/main` for every `TaskContractMismatch`, and now for most value
     errors - is reported there as INVALID_RESULT with
     `dispatch_may_have_occurred: true`, though nothing started. The fix is
     the door's: accept `field`, verify with
     `research_tools.registered_correction`, for any operation. This slice
     does not land before it. A test drives a value refusal through the real
     door,
     `test_a_value_refusal_crosses_the_standard_mcp_door_as_refused`. It is
     a strict xfail: once the door is fixed it passes, which strict mode
     reports as a failure until the mark is removed.
2. **The program's output is in its result.** Each run result (CPU, Julia,
   local GPU, remote GPU) carries `program_output`: `stdout_tail` and
   `stderr_tail`, the end of each stream, and on a nonzero exit `traceback`,
   the last Python or Julia traceback in stderr. Each is at most 4096 bytes
   as the result delivers it (`research_carrier.OUTPUT_TAIL_BYTES`), counted
   JSON-escaped, so a byte that is not UTF-8 (U+FFFD) or a control character
   counts for its six-byte escape and 4 KiB read never reaches the model as
   24 KiB. A traceback that fits is whole; a longer one keeps its first 2 KiB
   and its end, with the number of characters left out between them. Julia
   prints its error message first (`ERROR: LoadError: ...`) and where it
   started last; Python prints its exception last; both ends are kept. This
   is an engineering bound on what reaches a model's context per call, not a
   limit on the program: the kept 64 KiB stay in the operation folder
   (RSURF-D21). Only a flat `operation-...` folder name is read.
   - `program_output` reaches every campaign, historical rule included: it
     is new information in a run result, not a frozen rule, prompt or tool
     list, and replays read the retained result.
3. **What `read_file` returns is versioned with the tools rule.** Whatever a
   tool returns stays in the agent's context for the rest of its epoch, and a
   request is admitted only within `max_input_tokens` less a reserve (61440
   at the default selection).
   - Historical rule (no rule frozen): exactly as before, at most 4096 bytes
     as `content_base64` alone. A campaign frozen before this, Graphite's
     included, reads exactly what it read.
   - v2 rule: at most 8192 bytes, returned once
     (`research_tasks.read_file_content`): `content_utf8` when the bytes are
     UTF-8 text that JSON-escapes to no more than its base64, otherwise
     `content_base64`; the other is null. Ordinary text, JSON and source
     code come back as text; bytes, and text full of control or non-ASCII
     characters (up to six escaped bytes per byte), as base64. The v2
     description says so, and that a read stays in context.
   - Why 8192: measured against the real battery v2 first request (about 34
     KB) with no token anchor, the worst case one read may append - text one
     third quotes, kept as text and escaped again inside the history - fits
     at 8192 (53 KB of 61440) and does not at 12288 (61.5 KB). A test checks
     it from the real composition, prompt, tools and reply envelope,
     `test_one_maximal_read_fits_beside_the_battery_agents_first_request`.
   - The read cap's refusal lists the campaign's own maximum.
   - The Control Center page decodes `content_base64` today; for a v2
     campaign it must read `content_utf8` when that is not null (slice F).
4. **Each Challenge's own registry.** The executor names its Challenge
   (`PublicResearchExecutor.challenge`). Battery's composition sets it;
   omitted, it is Burgers', as before.
   - Capability requests, the roadmap and demand read that Challenge's
     registry.
   - Burgers' roadmap is unchanged byte for byte. Another Challenge's names
     itself.
   - A check-design verdict counts as demand only for its own Challenge.
   - A verdict for an unknown Challenge records no ids. Before, it raised
     inside the executor.
5. **A versioned tools rule; the historical tools stay byte-identical.**
   `research_tools.TOOLS` is unchanged and its digest is pinned in a test.
   Graphite's roles digest it, and frozen epoch plans record it.
   - `TOOLS_RULE` (`carbon.autoresearch.research-tools.v2`) has the same
     operations and schemas, with descriptions that say:
     - what each action takes and returns;
     - that `arguments_json` is an encoded string;
     - what `expected_digest` is;
     - the `device: cpu|gpu` choice;
     - that a run or a practice spends one research-trial slot, `run_julia`
       included;
     - that files written to `../output` (`/scratch/output`) are exported;
     - what `program_output` holds;
     - what `read_file` returns, and that it stays in context (decision 3);
     - what a refusal means.
   - A campaign freezes the rule in its run plan (`provider.research_tools`).
     `tools_for_sdk` reads it from the campaign's frozen manifest. Without
     it, the historical tools are offered. A rule the code does not know is
     refused, never read as the historical one.
   - Freezing the rule in battery's `provider_plan` is slice A's change.
     This slice does not own that function.
6. **The battery agent's research environment, under the same rule.** A
   campaign that froze the rule sees `research_environment` in its first
   observation:
   - whether its runtime has a GPU lane for code cells, and which;
   - which code-cell actions take `device=gpu` there: those the lane's own
     description lists among those the campaign offers, so a remote lane
     (run_python only) is never said to run run_julia;
   - the backends its practice serves on this host;
   - whether authored Julia is offered.

   It reads the composition's own executor and practice, never a default: a
   missing attribute is an error, not a quiet "cpu only".

   A practice whose recipe names an unserved backend is refused before
   dispatch with `backend_not_served`, listing the served backends
   (`BatteryPractice.backend_refusal`).
7. **Refusals name their tool and field.**
   - A wrong field set, an unknown tool, a JSON field that is not one object,
     a bad task id, an out-of-range integer, an unbounded hypothesis and an
     unknown action each get a registered code and field.
   - What no named check covers is `tool_value_invalid` on `arguments`, the
     tool still named, never the exception text behind it.
   - The correction text names the tool, never the requester's own text.
   - Corrections may list Carbon-written choices.
   - `research_tools.registered_correction` lets a door that forwards a
     refusal verify it is registered text.
   - `inspect_prior_alignment` is journalled as a refusal, not a capability
     request, so the demand stream holds only what the agent asked for.
8. **The compiler is not changed.** The domain specification
   (`Design_Specs/Candidate_Assembly_and_Strategy_Compiler_Contract.md`
   §10.4) fixes the compiler's codes and forbids dynamic diagnostics, and
   `strategy_limits` already names the exceeded capture limit at the
   research surface. `check_design` returns it as `limits_exceeded`, and the
   v2 description says so. Classified NO_CONFLICT; no owner input needed.
   Naming the limit beside a `dry_validate` or `compile_strategy` reply
   needs a `limits_exceeded` key the MCP door does not yet accept: a
   follow-up with slice B.
9. **The battery discovery document.**
   - `arguments_json` is shown as an encoded string.
   - `validate` points at `check_design`.
   - Freezing and submitting are named as the campaign's own steps, not
     research tools.
   - Progress text matches a start call that returns once its task has
     finished.
   - It states which backends practice serves.
   - Examples are designs as they stand (`{strategy}`), with their admission
     verdicts beside them in `examples_admission`. Readers of
     `examples[i]["strategy"]` are unchanged.

   This is a live public document, not a frozen record. A campaign is pinned
   to its exact accepted implementation revision, which `check_attached`
   compares on every attach. So no epoch plan frozen under the old text is
   ever rebuilt with the new one.

**Tests.** `tests/cpu/test_lp_prod_research_tools.py` (new). Updated, each
for a deliberate change stated in its own text:
- `test_cw1_research_tools.py`: the specimen names a wall allowance, and
  the shared-check assertion.
- `test_cw1_research_tasks.py`, `test_capability_demand.py` and
  `test_julia_research.py`: REQUEST_REFUSED replaces FAILED_INFRA for a
  refused value. `test_cw1_research_tasks.py` also asserts a campaign with
  no rule reads base64 alone.
- `test_challenge_registry.py`: the examples' shape.
- `test_gpu_code_cell.py`: local and remote GPU runs, succeeding and
  failing, return `program_output`.

## 2026-10-03 — W1 (integration wiring): one rule builds and verifies a correction, with closed lists of what it may list

**Authority.** Delegated engineering decisions (integration fixer W1), within
OWNER-LAUNCHPAD-PROD-01. Correction format only: no scientific value, live
economics, spend, chain write, exposure or authority boundary changes.

1. *Listed values come from closed public lists.* A correction's `choices`
   were checked only for shape (`_CHOICE`), so a private identifier of the
   same shape could have been listed and forwarded. `correction_choices(code)`
   now names each code's closed list - every material name any material
   service serves (`research_tasks.every_public_material_name`, over the new
   `PUBLIC_MATERIALS`), the reconstruction backends the capability registry
   registers, the per-call `read_file` maximum under each rule, notebook
   kinds, the carrier's own stage names and the remote wrapper's, and Julia
   environments - and is empty for a code that lists nothing.
   `TaskContractMismatch` refuses to build a correction listing anything else
   (it then falls to `tool_value_invalid`, still before dispatch).
2. *The door verifies with the same rule.* `correction_parts(value)` returns
   the registered parts a correction was built from, or None: it parses the
   code, field, listed values and tool, checks each against its registry,
   and requires the text to equal what `task_correction` builds from them.
   `registered_correction` is that with a field; the standard MCP door calls
   `correction_parts` (LP-PROD-B, W1). The executor's REQUEST_REFUSED result
   is unchanged.

Tests: `tests/cpu/test_lp_prod_wire_doors.py` (every code, field kind, listed
value, tool and null variant crosses the door; an unlisted value or another
tool never does; the closed lists hold what each producer lists). In
`tests/cpu/test_lp_prod_research_tools.py` the strict xfail of the door test
is removed, and `test_registered_correction_refuses_text_carbon_did_not_write`
lists a real material name and gains an unlisted one.
