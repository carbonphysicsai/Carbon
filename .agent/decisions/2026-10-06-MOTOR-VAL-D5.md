# MOTOR-VAL-D5 — Share public-practice custody by Challenge identity

**Ticket:** CHALLENGE-MOTOR-07. **Status:** implemented working engineering
decision; public DEVELOPMENT only.

**Problem:** Motor needs durable owner-only batch, reference, submission and
score custody. Copying Cooling's SQLite implementation would create two
security-sensitive stores with independently drifting behavior.

**Recommendation and location:** Extract `PublicPracticeStore` to
`carbon/challenge_validator/public_practice_store.py`. Its constructor
requires a Challenge-specific name, schema and typed error factory; it does
not know Battery, Cooling, Motor, scientific rules or private reference
material. `CoolingStore` and `MotorStore` bind their own identities and
preserve Cooling's existing file/schema/refusal codes. Challenge adapters,
not the store, validate exact pinned public records before ingestion.

**Alternatives rejected:** A Motor clone duplicates owner-only security and
transaction behavior. Importing `CoolingStore` directly would give Motor a
Cooling-named store and error contract. Broadly refactoring all validator
storage is outside this ticket.

**Affected boundaries:** Cooling and Motor Interface-v1 adapters, owner-only
SQLite custody, existing Cooling migration compatibility and operator/miner
separation. The shared store is pinned into each adapter's implementation
digest. Battery storage and live contract are untouched.

**Reversibility:** A future storage backend can replace this shared class
behind each Challenge adapter, preserving the Challenge-specific schema and
historical records. If the lead disagrees, the smallest superseding change is
to alter the shared constructor/adapter wrappers and their tests; do not
silently reinterpret previously scored submissions. No human-reserved value
is needed for this bounded engineering extraction.
