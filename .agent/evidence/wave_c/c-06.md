## Implemented flow

The trusted controller closes already-produced public DEVELOPMENT evidence by
digest. A caller-supplied development Ed25519 key signs one canonical receipt
that includes the exact three reconstruction attempts, frozen inference,
role-explicit reference, unresolved measurement result and all source/policy/
environment identities. The ledger verifies the signature, key issuance and
evidence closure, then atomically appends receipt bytes and a chained event.

Exact replay returns the prior reference without a new effect. Changed bytes
under the same ID reject. Corrections require a new signed receipt that appends
an explicit supersession event; revocation is also append-only. Reopening the
store verifies canonical receipt bytes and the entire hash chain before use.

## Disclosure and authority

The public projection discloses only receipt/challenge/submission/status/
lifecycle/signer/ledger identifiers and literal-false eligibility. The reviewer
projection additionally includes digest-only bindings, timing, supersession and
signature material. Neither view contains raw TRAIN, protected cases, answer
keys, seeds, numerical thresholds or private signing material.

Every receipt is mechanically non-official: protected, score, archive,
network and reward eligibility cannot be set true. Signing proves only the
named development key bound exact evidence. It does not prove scientific truth,
secure protected execution, durable real archive custody or authorization by an
independent reviewer.

## Candidate verification

Focused tests currently pass for exact round-trip/replay, distinct allow-lists,
missing evidence, signature tamper, stale/revoked keys, conflicting identity,
atomic rollback, supersession/revocation, persisted tamper/partial writes,
invalid transitions and authority-upgrade denial. Structural invariants confirm
there is no scoring, qualification, archive, network, reward or settlement
dependency. Exact accepted head/run/merge evidence remains pending.
